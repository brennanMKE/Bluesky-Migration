## Description

Discovered while writing the settings/moderation UI test suite (#0183). Two of the `UITestNavigator` intents shipped in the foundation (#0175) — `openSettings` and `openModeration` — do not reliably push their destination screens on iOS when driven via the launch-environment script. The settings/moderation suite had to navigate via the real own-profile menu path instead.

## Steps to reproduce

1. Launch the app under UI test with `BLUESKY_UI_TEST_SCRIPT=[{"intent":"selectTab","tab":"profile"},{"intent":"openSettings"}]`.
2. Observe whether `SettingsScreen` is pushed.

## Expected behavior

`openSettings` pushes `SettingsScreen`; `openModeration` pushes `ModerationScreen` — consistent with how `tapFirstPost` reliably pushes `ThreadView`.

## Actual behavior

The screen does not reliably appear; the navigator flag is set but the corresponding `MainTabView` navigation binding doesn't fire on the iOS push path.

## Notes

- The #0183 suite works around this by navigating through the own-profile menu (the real user path), so coverage is intact — but the driver intents themselves should be fixed so other suites/screens can rely on them.
- Likely a timing/binding issue in how `MainTabView` mirrors `UITestNavigator.shouldOpenSettings` / `shouldOpenModeration` into its `showSettings` / `showModeration` `@State` on iOS. Compare against the `threadURI` (tapFirstPost) path, which works.
- Relevant files: `Bluesky-SwiftUI/Bluesky-SwiftUI/UITestNavigator.swift`, `Bluesky-SwiftUI/Bluesky-SwiftUI/MainTabView.swift`.

## Root cause

A race in `UITestNavigator`. The `openSettings` / `openModeration` intents set `selectedTab = .profile` **and** the `shouldOpenSettings` / `shouldOpenModeration` flag in the same synchronous block. But switching the tab (a) fires `MainTabView`'s `resetTransientNavState()` `onChange`, which clears those flags, and (b) the Profile tab's `NavigationStack` and its `navigationDestination(isPresented:)` aren't mounted until after the switch settles. So the flag was raised before the destination existed and was then cleared by the reset — sometimes dropping the push on iOS. The `tapFirstPost` path doesn't hit this because it waits for the feed before setting `threadURI`.

## Fix

In `UITestNavigator`, `await` a short settle (`settleAfterTabSwitch()`, ~0.3s) after `selectedTab = .profile` and before raising the `shouldOpen*` flag, so the tab-switch view update + reset have run and the Profile destination is mounted when the flag is set — mirroring the reliable `tapFirstPost` ordering. (Code: Bluesky-SwiftUI `11af59d`.)
