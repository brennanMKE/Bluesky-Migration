## Description

The Mac app has no update mechanism — Sparkle is not present anywhere in the project (verified 2026-06-10: no `Sparkle`/`SUFeedURL` references in the pbxproj or xcconfigs). Integrate Sparkle for automatic updates fed by an appcast on the release website (#0191), following the working pattern in `~/Developer/brennanMKE/Batty`.

## Expected behavior

The macOS app checks an appcast feed for updates, offers a "Check for Updates…" menu item, and installs signed updates automatically — like Batty does.

## Actual behavior

No Sparkle integration; the only way to update is replacing the app manually.

## Notes

Model directly on Batty (`~/Developer/brennanMKE/Batty`), which is the proven reference:

- **Dependency:** Sparkle via SPM. Batty declares it in `BattyKit/Package.swift`; the analogous home here is `BlueskyKit/Package.swift` or directly on the app target (macOS-only — guard so iOS targets don't pull it in).
- **Controller:** Batty wraps Sparkle in `BattyKit/Sources/BattyKit/Updater/UpdaterController.swift`; create the equivalent (e.g. in the app target or a small macOS-only module) and add the "Check for Updates…" item to the app menu / Commands.
- **Info.plist keys via xcconfig**, matching the existing Beta/Prod layering (#0173). Per the `mac-release` skill (`references/sparkle.md`), the cleanest wiring is a real `Info.plist` whose `SUFeedURL`/`SUPublicEDKey` entries reference build settings defined in xcconfig:
  ```
  SU_FEED_URL = $HTTPS/<release-site-domain>/appcast.xml
  SU_PUBLIC_ED_KEY = <EdDSA public key>
  ```
  Batty leaves these empty in the base xcconfig and fills them per variant — decide whether Bluesky's Beta and Prod builds share one feed or get separate channels (separate bundle IDs already exist, so separate feeds are natural).
- **EdDSA keys:** after SPM resolves Sparkle, `generate_keys`/`sign_update` land under `SourcePackages/artifacts/sparkle/Sparkle/bin/`. Generate with a **per-app `--account`** (e.g. `--account Bluesky`) so keychain entries don't collide with Batty's; the same account name must be used by `sign_update` at release time. Export and back up the private key — losing it strands existing installs. Public key → `SU_PUBLIC_ED_KEY`. (Batty's `scripts/setup-keys.sh` + `SPARKLE.md` are local references.)
- **Versioning:** Sparkle decides "is there an update?" by comparing the appcast's `sparkle:version` against the running `CFBundleVersion`, while showing marketing strings in the dialog — so `MARKETING_VERSION`/`CURRENT_PROJECT_VERSION` must be managed deliberately (xcconfig as source of truth, no pbxproj overrides). The release pipeline (#0191) carries the guards.
- **Prerequisite for updates to install on real Macs:** Developer ID signing + notarization of the released app/DMG — that's [#0191](0191.md). In-app integration can land and be tested first with a local/dev feed.
