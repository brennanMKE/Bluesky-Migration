# 0197 — Composer media posts rejected by PDS: `BlobRef` encodes without `$type: "blob"`

| | |
|---|---|
| **Status** | open |
| **Module** | BlueskyCore / BlueskyComposer |
| **Platform** | All |
| **First seen** | 2026-06-10 |

## Description

Submitting any post that carries a blob embed fails server-side with an
`InvalidRequest` from the PDS. The blob reference the app writes into the
record is missing the required `$type: "blob"` discriminator, so lexicon
validation rejects the record. This breaks, at minimum:

- **Image posts** — `app.bsky.embed.images` (`$.record.embed.images[N].image`)
- **Link-card posts with a thumbnail** — `app.bsky.embed.external.thumb`
- **Video posts** — `app.bsky.embed.video.video` (same encode path; not live-confirmed because the failing image/link cases already burn the submit, but the code path is identical)
- **GIF posts** — `app.bsky.embed.external` with a `thumb` blob (same path)

Found while running the #0064 composer gate on the iPhone 17 simulator
(iOS 26.5): the gate's image post and link-card post both failed at submit
with this error; the plain-text + mention post (no blob) succeeded.

## Steps to reproduce

1. Sign in, open the composer.
2. Type any text, attach an image (or paste a URL and let the link card resolve a thumbnail).
3. Tap Post.

## Expected behavior

The blob upload succeeds (it does) and the post record references the
uploaded blob in the AT Proto blob shape:

```json
{ "$type": "blob", "ref": { "$link": "<cid>" }, "mimeType": "image/png", "size": 1234 }
```

RN round-trips the `BlobRef` returned by `uploadBlob` verbatim, `$type`
included, so its records validate.

## Actual behavior

Alert: **Post failed — “Invalid app.bsky.feed.post record: Expected blob value
type (got {"mimeType": ..., "ref": ..., ...}) at $.record.embed.images[0].image”**
(image post), and the same at `$.record.embed.external.thumb` (link card with
thumbnail). No post is created.

## Notes

- Root cause: `BlueskyKit/Sources/BlueskyCore/Embed.swift` — `BlobRef.encode(to:)`
  (lines ~48–53) writes only `ref`, `mimeType`, and `size`; it never writes
  `$type: "blob"`. Decoding works (the decoder ignores the extra `$type` the
  server sends), so the bug only surfaces on the write path — which was never
  live-validated until the #0064 gate run.
- Fix shape: add `case type = "$type"` to `BlobRef.CodingKeys` and encode the
  constant `"blob"`, leaving the decoder lenient (don't require `$type` on
  reads — some legacy records carry the deprecated `{cid, mimeType}` shape).
- Blast radius beyond the composer: anything that re-encodes a `BlobRef` into
  a record write (e.g. profile avatar/banner updates via `putRecord`, if they
  reuse this type) has the same latent bug and should be checked when fixing.
- Blocks #0064 live checks: image post, alt-text round-trip, video post, and
  the link-card submit half.
