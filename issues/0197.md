# 0197 — macOS: post button should be a floating button at the bottom right, as in the RN app

## Description

On macOS the post composer is opened from a toolbar button. It should instead be a floating circular button at the bottom-right of the feed, matching the RN iPhone app. The iPhone build already does this (the iOS-compact FAB owns composition per `MainTabView.swift` ~line 851); macOS needs the same treatment. Reference implementation in the prototype at `~/Developer/Bluesky/MacBlueskyNav` (`HomeFeedView.swift` ~lines 63–78).

## Steps to reproduce

1. Launch the Mac app and sign in.
2. Look for the compose affordance on the Home tab.

## Expected behavior

A floating circular `square.and.pencil` button (56×56, accent background, shadow) anchored bottom-trailing over the feed opens the composer — as in the RN app and the prototype.

## Actual behavior

Compose lives in the window toolbar (`MainTabView.swift` ~line 877, `ToolbarItem(id: "bsky.compose", placement: .primaryAction)`), contributing to the crowded trailing toolbar ([#0196](0196.md)).

## Notes

- Prototype details worth mirroring: `ZStack(alignment: .bottomTrailing)` over the feed list, `.buttonStyle(.plain)`, 20pt trailing/bottom padding. The prototype also stages a bottom-left "new posts" button in the same ZStack — out of scope here, but keep the layout compatible.
- The existing iOS-compact FAB may be reusable; consider extracting it rather than writing a second one.
- **Do not copy screenshots from the prototype project — they are private images.** Reference its source only.

## Relation

- Pairs with: [#0196](0196.md), [#0198](0198.md) — together these adopt the prototype's RN-style navigation on macOS.

## Review

### Round 1 — 2026-06-11 — claude-opus-4-8

**Verdict: Request changes**

The FAB itself is correct — right glyph (`square.and.pencil`), 56×56, `theme.colors.link` circle (resolves on macOS; the property body has no platform-specific APIs), shadow, bottom-trailing, 20pt padding matching the prototype. Placing it as an `.overlay(alignment: .bottomTrailing)` on the detail `NavigationStack` so it floats over pushed destinations is right and matches RN: in RN desktop `ComposeBtn` lives in the persistent `LeftNav` shell (`LeftNav.tsx:809`), present on every route, driven by a global `useOpenComposer()` action — so showing it on all tabs except Messages is correct parity. iOS is untouched (the `iosCompactLayout` overlay at ~line 441 still uses 16pt padding and its own root-level sheet) and the macOS build succeeds.

But there is one blocking correctness bug:

1. **FAB is a dead button on every macOS tab except Home.** `MainTabView.swift` — the FAB sets `showComposer = true`, but on macOS the only `ComposerSheet` presenter is `.sheet(isPresented: $showComposer)` attached inside `tabContent(.home)` (line ~951). The macOS shell (`body` → `macOSSidebar`, lines 130–165) has no shell-level composer sheet, and the `.search`, `.notifications`, `.saved` (Feeds), and `.profile` cases of `tabContent` do not attach one either. Since `sidebarTabs == allCases` and the FAB now renders on home, search, notifications, saved, and profile, tapping it on the four non-home tabs flips `showComposer` with nothing observing it — the composer never opens. (On `main` this was latent because the toolbar compose button had already been removed in #0196 and there was no compose affordance on those tabs at all; this branch makes the broken affordance visible.)

   **What would satisfy:** hoist the composer presenter to the macOS shell so it works regardless of the active tab — e.g. attach `.sheet(isPresented: $showComposer) { ComposerSheet(...) }` once on `macOSSidebar` (alongside the existing shell modifiers in `body`), and remove the now-redundant home-only macOS sheet at line ~951. This mirrors RN's global `openComposer`. Verify by launching the Mac app, switching to the Search (or Notifications/Feeds/Profile) tab, and confirming the FAB opens the composer there — the current verification only exercised Home.

Layout compatibility with a future bottom-left "new posts" button (#0195) and the #0198 sidebar→drawer restructuring is fine: the overlay is anchored on the NavigationStack independent of the split-view chrome, and hoisting the sheet to the shell makes it even more robust to that restructuring.

### Round 2 — 2026-06-11 — claude-opus-4-8

**Verdict: Approve**

The round-1 blocker is properly fixed. The composer presenter is now attached at the macOS shell: `.sheet(isPresented: $showComposer) { ComposerSheet(network: env.network, accountStore: env.accounts, preferences: env.preferences) }` sits at the tail of the `macOSSidebar` modifier chain in `body` (MainTabView.swift:169–171), after `UITestDriverModifier`. Confirmed it modifies the whole shell, not a sub-branch: the `#if os(macOS)` branch of `body` is a single chained expression rooted at `macOSSidebar`, and the FAB overlay (lines 348–354) is on the detail `NavigationStack` inside that shell — so for every tab where the FAB renders (`selectedTab != .messages`), the same `showComposer` toggles a live presenter. Verified by tracing the FAB's `showComposer = true` (line 755) to the single shell sheet.

Arguments match the removed home-only sheet byte-for-byte (`git show main:` confirms identical `ComposerSheet(network:accountStore:preferences:)` at all sites). No double-presentation on macOS: `grep` shows exactly one `.sheet(isPresented: $showComposer)` reachable on macOS (line 169) — the home-tab sheet that previously sat under `#if os(macOS)` was removed and its `#else` correctly re-guarded to `#if os(iOS)` (line 958), so iPad-regular still presents at `.regular` width and iOS-compact's root sheet (line 465) is untouched. iOS is functionally byte-for-byte equivalent: the only iOS token in the diff is the `#else`→`#if os(iOS)` rename, which is semantically identical now that macOS no longer has a branch there; the toolbar compose `ToolbarItem` stays fully `#if os(iOS)`-guarded (lines 868–882), so macOS gains no toolbar regression and #0196 stays intact. `composeFAB` was relocated under a new "Shared UI components" mark with an identical body. No scope creep into #0198 (sidebar untouched; overlay anchored independent of split-view chrome). macOS build succeeds (only pre-existing SDKROOT xcconfig warnings).
