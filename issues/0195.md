## Description

The macOS app aborts on launch roughly **1 in 4 times** with a Swift-runtime
generic-metadata failure inside `_AVKit_SwiftUI`. When it happens the process
dies before any window is created (the menu bar appears, then the app aborts),
and macOS shows a "Bluesky Beta quit unexpectedly" Problem Reporter dialog. When
it doesn't happen, the app launches normally. iOS is unaffected.

This is a pre-existing bug — it was surfaced while bringing up the macOS UI-test
foundation (#0186), which is *blocked by this crash* (XCUITest sees an app with a
menu bar and zero windows whenever a launch hits the crash). It is tracked
separately here because it is a real app/runtime bug independent of the test
infrastructure.

## Steps to reproduce

1. Build the macOS app (Beta scheme): `xcodebuild build -workspace
   Bluesky.xcworkspace -scheme "Bluesky (Beta)" -destination 'platform=macOS'
   -allowProvisioningUpdates`.
2. Launch the built `Bluesky Beta.app` (e.g. double-click, or one `open -n`).
3. Repeat a handful of times. **Do NOT use a tight relaunch loop** — each crash
   spawns a Problem Reporter modal that cannot be dismissed programmatically and
   interrupts the user (see [[no-app-relaunch-loops]] note; clear stuck dialogs
   with `killall "Problem Reporter"`).

Measured rate: **5/20** crashes baseline (~25%).

## Expected behavior

The app opens its window on every launch.

## Actual behavior

~25% of launches abort with `SIGABRT` before the window is created. No window →
`app.windows.count == 0` under XCUITest with `app.state == runningForeground`.

## Crash signature

`SIGABRT` / `abort()`, main thread, at launch:

```
swift::fatalError
getSuperclassMetadata
_swift_initClassMetadataImpl
_AVKit_SwiftUI  __swift_instantiateGenericMetadata
swift_getAssociatedTypeWitnessSlow
swift_getTypeByMangledName…
(decoding a dependent member / associated-type witness)
```

i.e. a **race instantiating `_AVKit_SwiftUI` generic metadata** — two threads
demand the same metadata during launch and `getSuperclassMetadata` fails. This is
a known class of Swift-runtime metadata race. AVKit SwiftUI (`VideoPlayer`) is
used in:

- `BlueskyKit/Sources/BlueskyUI/VideoEmbedPlayer.swift`
- `BlueskyKit/Sources/BlueskyFeed/VideoFeedView.swift`

## Attempted fix (did NOT work — reverted)

`import AVKit` in the app target + `_ = VideoPlayer<EmptyView>.self` metadata
pre-warm in `Bluesky_SwiftUIApp.init()`. Re-measured: **10/20 (~50%)** — no
improvement (rapid relaunch is itself noisy/race-amplifying). Both app-code
changes were reverted.

## Notes / next steps

- Get a **symbolicated** crash report to identify the *exact* failing AVKit
  SwiftUI type — the pre-warm above may have targeted the wrong generic
  (`VideoPlayer<EmptyView>` vs whatever internal type actually fails).
- Try an explicit **"Link Binary With Libraries" → AVKit.framework /
  AVFoundation.framework** entry on the app target (not just `import`), so the
  framework + its class metadata load eagerly at launch.
- Check whether the **macOS deployment target (15.6) vs the macOS 26 SDK/runtime**
  is implicated (weak-linked AVKit SwiftUI symbols).
- Consider whether any view in the *initial* graph transitively forces AVKit
  SwiftUI metadata at launch, and defer it.
- **Validate any fix with a small number of clean, single launches** — never a
  relaunch loop.
- Blocks #0186 (and therefore #0187–#0194): macOS UI tests cannot run reliably
  until launches are crash-free.

## Root cause

The crash report (`Bluesky Beta-2026-06-10-182753.ips`) shows both sides of the
race directly. **Main thread:** SwiftUI's *initial* view-graph build reaches an
AVKit SwiftUI representable (`ViewResponderFilter.init` →
`swift_getAssociatedTypeWitness` → `_AVKit_SwiftUI
__swift_instantiateGenericMetadata` → `_swift_initClassMetadataImpl` →
`getSuperclassMetadata` → `swift::fatalError`). **Thread 2:** AttributeGraph's
background `TypeDescriptorCache::drain_queue` (utility QoS) is concurrently
walking the same not-yet-complete metadata via `swift_conformsToProtocol` →
`getSuperclassForMaybeIncompleteMetadata` → `swift_checkMetadataState`.
**Thread 7** shows an `AVPlayer` being constructed during launch — the home
feed renders instantly from cache (#0048), and when the cached feed contains a
video embed, `VideoEmbedPlayer` mounts SwiftUI's `VideoPlayer` (from the
`_AVKit_SwiftUI` cross-import overlay) inside the very first view graph, right
when AttributeGraph's background descriptor thread is busiest. Two threads
instantiate the same `_AVKit_SwiftUI` generic class metadata concurrently and
the runtime aborts — hence intermittent (~25%) and launch-only.

## Fix

Removed the `_AVKit_SwiftUI` overlay from the process instead of trying to
out-race it. New non-generic `BlueskyVideoView` representable in `BlueskyUI`
(named after RN's native `BlueskyVideoView`) wraps the platform players
directly — `AVPlayerView` on macOS, `AVPlayerViewController` on iOS — with a
`showsControls` flag. All three `VideoPlayer` call sites now use it:
`VideoEmbedPlayer` inline surface (no controls), `FullscreenVideoSheet`
(controls), and `VideoFeedView`'s `VideoPostPage` (no controls). With no
reference to `VideoPlayer` left, the `_AVKit_SwiftUI` overlay is no longer
autolinked, so its generic metadata can never be instantiated — the crash is
structurally impossible, not just less likely. When `showsControls` is false
the surface sets `allowsHitTesting(false)`, replacing the old
`.disabled(true)` trick that let cell tap gestures win.

## Verification

- `swift build` (BlueskyKit, macOS) and `xcodebuild build -workspace
  Bluesky.xcworkspace -scheme "Bluesky (Beta)"` for both `platform=macOS` and
  `generic/platform=iOS Simulator` — all succeeded (both representable
  branches compiled).
- **Structural check:** `otool -L` on the rebuilt `Bluesky Beta` binary and
  `Bluesky Beta.debug.dylib` lists only `AVKit.framework` —
  `_AVKit_SwiftUI` is gone from the load commands, so the faulting image
  cannot load into the process at all.
- **Single clean launch** (per the no-relaunch-loop rule): app alive 8s after
  `open -n` (baseline crash fired ~2.3s after launch), quit cleanly via
  AppleScript, DiagnosticReports count unchanged (17 before and after).
  Repeated relaunch sampling was deliberately not performed; the structural
  check above is the primary evidence.

## Files changed

- `BlueskyKit/Sources/BlueskyUI/BlueskyVideoView.swift` — new: non-generic
  `NSViewRepresentable`/`UIViewControllerRepresentable` video surface wrapping
  `AVPlayerView` / `AVPlayerViewController`.
- `BlueskyKit/Sources/BlueskyUI/VideoEmbedPlayer.swift` — inline and
  fullscreen branches use `BlueskyVideoView` instead of `VideoPlayer`.
- `BlueskyKit/Sources/BlueskyFeed/VideoFeedView.swift` — `VideoPostPage` uses
  `BlueskyVideoView` instead of `VideoPlayer`.

## Gotchas

- The earlier `VideoPlayer<EmptyView>.self` pre-warm failed because the
  failing generic is *internal* to `_AVKit_SwiftUI` (reached through an
  associated-type witness of the overlay's private representable), not
  `VideoPlayer` itself. Pre-warming the right type from app code isn't
  reliably possible; unlinking the overlay is.
- `import AVKit` + `import SwiftUI` in the same file does **not** by itself
  keep `_AVKit_SwiftUI` linked — the overlay is only autolinked when one of
  its symbols (e.g. `VideoPlayer`) is referenced. Verified via `otool -L`
  after the change.
- The launch-time trigger was cached feed content: the feed renders from
  `SwiftDataCacheStore` before any network round-trip, so a video embed can
  sit in the *first* view graph. Any AVKit-SwiftUI usage that can appear in
  the initial graph is exposed to this runtime race on macOS 26.
