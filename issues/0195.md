# 0195 — Incoming DMs do not appear until the conversation is reloaded: add getLog polling while messages UI is visible

| | |
|---|---|
| **Status** | open |
| **Module** | BlueskyMessages |
| **Platform** | All |
| **First seen** | 2026-06-11 |

## Description

Messages sent from another account do not appear in an open conversation until the view is reloaded. The app has no live-update mechanism for DMs. Push notifications are not required for parity: the RN client keeps chats current by polling `chat.bsky.convo.getLog` on a visibility-scaled interval, and the SwiftUI app should do the same.

## Steps to reproduce

1. Sign in on two devices/accounts and open the same conversation on both.
2. Send a message from account B.
3. Watch account A's open conversation view.

## Expected behavior

The new message appears in account A's conversation within a few seconds without any manual action (RN polls every 4 s while a conversation is open and foregrounded).

## Actual behavior

User report: "when I send a message from the other account it does not appear right away" — it only shows up after the view is reloaded.

## Notes

RN reference implementation (`../Bluesky-ReactNative/`):

- `src/state/messages/convo/const.ts` — `ACTIVE_POLL_INTERVAL = 4e3` (convo open + app foregrounded), `MESSAGE_SCREEN_POLL_INTERVAL = 30e3` (conversation-list screen), `BACKGROUND_POLL_INTERVAL = 60e3`.
- `src/state/messages/events/agent.ts` (~line 246) — a single shared events agent calls `chat.bsky.convo.getLog(cursor:)` on a timer; consumers request the interval they need and the agent runs at the minimum requested. `getLog` returns incremental events (new message, delete, read-state) since the cursor, so one poll updates both the thread and the conversation list (unread badges).
- `src/state/messages/convo/agent.ts` — the convo screen requests `ACTIVE_POLL_INTERVAL` while visible and drops to background interval when not.

Suggested SwiftUI shape: a polling task owned by `ConversationStore` (or a new events store) started/stopped from the messages screens via `.task`/`onDisappear` (structured-concurrency timer loop, honoring the explicit-actor isolation rules in the architecture docs), interval chosen by which messages surface is frontmost. `getLog` needs the same `atproto-proxy: did:web:api.bsky.chat#bsky_chat` header as other `chat.bsky.*` lexicons — already handled by `ATProtoClient.applyProxyHeader`.

Push notifications for DMs remain out of scope here (the app is not set up for notifications; see #0030 for notification routing work).
