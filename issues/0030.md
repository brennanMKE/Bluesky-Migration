## Description

When a push notification is received (like, reply, follow, mention), tapping it should navigate directly to the relevant post thread or profile. This deep-link handling from APNs is not implemented.

## Steps to reproduce

1. Register for push notifications (requires `app.bsky.notification.registerPush`).
2. Have another account like or reply to one of your posts.
3. Tap the push notification banner.

## Expected behavior

The app opens and navigates directly to the relevant thread or profile.

## Actual behavior

Push notification registration is not implemented, and no APNs payload handler exists in the app delegate / `SceneDelegate`. Tapping a notification likely does nothing or just opens the app to its current state.

## Notes

Requires: (1) APNs entitlement in the Xcode project, (2) `registerPush` call in `SessionManager` after login, (3) `UNUserNotificationCenterDelegate` in the app target to parse the payload and call the deep-link router.

## Root cause

Three pieces were missing or wrong:

1. **No payload → route logic matching the RN spec.** The old
   `PushNotificationDelegate` ad-hoc-parsed only `follow` (via a non-existent
   `author` key) and "everything else → subject-or-uri", which diverges from
   RN's `notificationToURL` (`src/lib/hooks/useNotificationHandler.ts`):
   like/repost families route on `subject`, reply/quote/mention/subscribed-post
   on `uri`, follow/starterpack-joined to the *profile* of the `uri` record's
   repo, chat reasons to a conversation/inbox, verified/unverified to the
   notifications list — with an `app.bsky.feed.post` collection check before
   opening a thread.
2. **Dead and racy navigation glue.** The `openProfile` path set a
   `pushProfileDID` `@State` that no `navigationDestination` ever consumed
   (follow taps dead-ended), and `openPostThread` set `selectedTab = .home`
   plus `threadURI` in the same turn — but `onChange(of: selectedTab)` calls
   `resetTransientNavState()`, which nils `threadURI`, so routing from any
   other tab self-destructed. Cold-start taps (delegate fires before
   `MainTabView` mounts) were dropped entirely because the route was posted
   into a `NotificationCenter` with no observers yet.
3. **No registration.** Nothing requested notification authorization, captured
   the APNs device token (no `UIApplicationDelegate` existed under the SwiftUI
   lifecycle), or called `app.bsky.notification.registerPush`.

## Fix

- **`BlueskyKit/Sources/BlueskyNotifications/PushNotificationRouting.swift`
  (new):** `PushNotificationPayload` (parses the RN payload keys `reason` /
  `uri` / `subject` / `convoId` / `recipientDid` from APNs `userInfo`) and
  `PushNotificationRoute` (`postThread` / `profile` / `conversation` /
  `messagesInbox` / `notificationsTab`) implementing RN's `notificationToURL`
  rules verbatim, both `nonisolated` so delegate callbacks can parse anywhere.
  `PushRegistrationService` posts the RN-shaped `registerPush` body
  (`serviceDid: did:web:api.bsky.app`, hex token, `platform: ios`,
  `appId:` bundle id).
- **`Bluesky-SwiftUI/PushRouter.swift` (rewritten):** the delegate is now a
  thin parse-and-forward shim into a buffering `PushRouteDispatcher`
  (solves cold-start: `MainTabView` consumes the buffered route from `.task`
  as well as on the `.pushRouteReceived` notification). `PushAppDelegate`
  (`@UIApplicationDelegateAdaptor`) captures the device token;
  `PushRegistrationCoordinator` registers it once a session is active and
  prompts for permission only while `notDetermined` (never under test
  launches). A `BLUESKY_SIMULATE_PUSH_TAP` launch variable drives the same
  parse → dispatch path for simulator verification.
- **`Bluesky-SwiftUI/MainTabView.swift`:** `applyPendingPushRoute()` maps
  routes onto navigation state — threads/profiles push on the Home stack (RN
  parity), chat → Messages tab, fallback → Notifications tab. Tab-switching
  routes park their destination in `pendingPushThreadURI/-ProfileDID`, which
  `resetTransientNavState()` re-applies one tick after the reset; removed the
  dead `pushProfileDID`. Registration activates from a
  `.task(id: session.currentAccount?.did)`.
- **`Bluesky_SwiftUIApp.swift`:** the iOS `@UIApplicationDelegateAdaptor`
  property (the `aps-environment` entitlement was already committed
  previously).
- **Test repair (pre-existing breakage):** `swift test` had not compiled since
  `BlueskyEnvironment` gained `bookmarks`/`pathMonitor` (#0057/#0059) — added
  the missing mocks — and the bookmark negative-decode test still asserted a
  throw that #0154's lenient per-item decoding intentionally removed.

## Gotchas

- **`registerPush` returns 500 for this client.** Bluesky's gateway pushes
  through *its* APNs certificate, which is keyed to the official bundle id;
  registrations with `appId co.sstools.Bluesky.beta` are rejected server-side
  (`Internal Server Error`). Real end-to-end pushes need a relay/self-hosted
  notification service — pre-existing open question from the 2026-05-05 notes.
  The client-side path (registration call, receipt, parse, route) is what this
  issue covers and is in place.
- **First production launch now shows the notification-permission alert**
  (once, while `notDetermined`) — intended RN-parity behavior; test launches
  (`BLUESKY_UI_TEST_SCRIPT` / `BLUESKY_SIMULATE_PUSH_TAP`) suppress it because
  nothing can answer the system alert in automation.
- **Don't build the simulator app with `CODE_SIGNING_ALLOWED=NO` if you intend
  to install it**: stripping entitlements changes keychain access and the
  installed app loses the saved session. Build with default signing for the
  install step.
- Chat routes land on the Messages inbox, not the specific conversation —
  `ConversationListScreen` has no external "open convo" entry point yet.
