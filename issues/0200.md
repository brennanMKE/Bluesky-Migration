## Description

The **Settings → Appearance → Font Size** tier picker (XS / S / M / L / XL) persists correctly (`appearance.fontSize` in `AppearanceStore`, survives force-quit + relaunch) and re-renders the in-screen preview sentence at the selected body point size — but **nothing else in the app reads the preference**. Feed text, thread text, profile text, etc. render at the same size regardless of the selected tier.

A repo-wide search confirms `AppearanceStore.fontSize` / `AppearanceFontSize.bodyPointSize` have no consumers outside `AppearanceSettingsScreen` (the preview `Text`) and the store itself. The shell modifier (`AppearanceShellModifier` in `Bluesky_SwiftUIApp.swift`) applies `preferredColorScheme` and `blueskyTheme` but never maps the font tier into the environment (e.g. via `.dynamicTypeSize(_:)` or a theme typography scale).

The same applies to the **Font** (System / Theme) family picker: `AppearanceFontFamily` is persisted but never read by the rendering layer (partially by design — no branded font is bundled — but the size tier is supposed to work).

## Steps to reproduce

1. Open Settings → Appearance and note the Home feed's text size.
2. Select **XL** in the Font Size picker. The preview sentence grows (16 → 18 pt).
3. Switch to the Home tab: feed text is unchanged.
4. Pixel comparison of Home-feed screenshots at M and XL shows identical text rendering.

## Expected behavior

Per the Module 14 gate (#0065/#0037): "Drag the Font Size slider … confirm text in the feed reflects it." RN scales app-wide typography from its `fontScale` shell preference through ALF (the font-size tiers in `AppearanceSettings` feed the ALF text atoms), so the selected tier must scale body text across feeds, threads, profiles, and settings. (Local RN checkout is missing from disk — confirm the exact upstream file when wiring the fix.)

## Actual behavior

Only the preview sentence inside `AppearanceSettingsScreen` changes. All other text is fixed at the default scale.

## Notes

- Persistence itself passes: `SettingsGateUITests.testFontSizeImmediateEffectAndPersistence` (#0065) confirms the XL selection survives force-quit + relaunch and the preview scales immediately.
- Likely fix: extend `AppearanceShellModifier` to translate `appearance.fontSize` into the SwiftUI environment — either `.dynamicTypeSize(...)` mapped per tier, or a body-point-size environment key consumed by `BlueskyUI` typography.
- Found while validating #0065 (Module 14 gate, iOS settings persistence).

## Root cause

`AppearanceStore.fontSize` was persisted and rendered in the Appearance screen's preview sentence, but the tier was never translated into anything the rendering layer reads. `AppearanceShellModifier` injected `preferredColorScheme` and `.blueskyTheme(_:)` only, and every `BlueskyUI` text element builds its font from the static `Typography` constants (`Font.system(size:)` — fixed sizes that also ignore Dynamic Type), so feed/thread/profile text was pixel-identical across all five tiers.

## Fix

**Approach — environment-driven scale multiplier** (the `blueskyAutoplayVideos` `@Entry` precedent, applied where fonts are built):

- `AppearanceFontSize.scaleMultiplier` (BlueskyKit) — tier → multiplier, derived as `bodyPointSize / 16` so the Appearance preview and the app-wide scale can never drift.
- `EnvironmentValues.blueskyFontScale` `@Entry` + `.blueskyFontScale(_:)` modifier and scaled `Typography` factories (`body(scale:)`, `headline(scale:)`, …) in `BlueskyUI/Tokens.swift`.
- `AppearanceShellModifier` (app shell) injects `.blueskyFontScale(appearance.fontSize.scaleMultiplier)` next to `.blueskyTheme(_:)`.
- The main reading surfaces consume it: `RichTextView` now takes an unscaled `baseSize` (instead of a prebuilt `Font`) and multiplies in the environment scale; `PostBodyView`, `PostCard` (author header, timestamp, banners, translate link, action counts), `FocalPostCard`, and `PostEmbedView` (link cards, quote posts) scale all their text. Notification-row post previews scale for free via `PostBodyView`.

**Why not `.dynamicTypeSize(_:)`:** all app text is built from `Typography`'s fixed `Font.system(size:)` constants, which do not respond to Dynamic Type, so a type-size override would have scaled nothing (and would have coupled the tier to system chrome). The environment multiplier matches RN's mechanism exactly instead.

**RN multiplier mapping** (ALF `computeFontScaleMultiplier`, `src/alf/fonts.ts` at baseline `46b8a58`, applied via `normalizeTextStyles` in `src/alf/typography.tsx`): RN steps `fontScale` by `factor = 0.0625` (1/16) — `'-1'` → 0.9375, `'0'` → 1, `'1'` → 1.0625; the scaffolded `'-2'`/`'2'` tiers are clamped to the ±1 values and commented `// unused`. Our picker already shipped five distinct body sizes (14–18 pt, #0065), so XS/XL extend the same linear 1/16 step rather than collapsing onto S/L:

| Tier | Multiplier | Body pt | RN slot |
|------|-----------|---------|---------|
| XS | 0.875 | 14 | `'-2'` (extended; RN clamps to 0.9375) |
| S | 0.9375 | 15 | `'-1'` |
| M | 1.0 | 16 | `'0'` (default) |
| L | 1.0625 | 17 | `'1'` |
| XL | 1.125 | 18 | `'2'` (extended; RN clamps to 1.0625) |

Persisted key (`appearance.fontSize`) and raw values (`xs`/`s`/`m`/`l`/`xl`) are unchanged — existing stored prefs keep working (guarded by a unit test).

**Bonus parity fix:** the focal post body now actually renders at RN's `text_lg` (18 pt × scale). The previous outer `.font(Typography.bodyLarge)` on `PostBodyView` was dead code — `RichTextView` set its own font on the inner `Text`, which always won.

**Intentionally unscaled surfaces** (chrome, not reading surfaces; RN scales everything through its text atoms, recorded as accepted divergence): navigation/tab chrome, settings screens (including the Appearance screen itself — its preview uses `bodyPointSize` directly), `FeedCard`/`ListCard` discovery cards, `MyFeedsScreen`/`ListDetailScreen` labels, `ProfileHeaderView` bio and known-followers chip, ThreadView's hidden-replies chrome, and icon glyph sizes (RN icons are not text atoms either).

## Gotchas

- `Font.system(size:)` does not respond to Dynamic Type, so a `.dynamicTypeSize(_:)` shell override would have scaled nothing — any future move to semantic styles must revisit this.
- `RichTextView` sets its font on the inner `Text`, so an outer `.font(...)` modifier on `PostBodyView`/`RichTextView` is silently ignored; pass `baseSize` instead.
- The focal post body grew from 16 pt to 18 pt (× scale) as a side effect of fixing that dead modifier — this is the documented RN parity (`text_lg` in `ThreadItemAnchor`), not a regression.
- The `Font` (System / Theme) family picker remains render-inert by design (no branded font bundled); this issue covered the size tier only.
