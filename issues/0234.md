# 0234 — Launch-time feed and preference fetches are cancelled mid-flight and logged as errors

| | |
|---|---|
| **Status** | open |
| **Module** | BlueskyFeed / BlueskySettings / BlueskyNetworking |
| **Platform** | macOS |
| **First seen** | 2026-06-10 |

> _Re-homed from **#0185** (Mac/MacBook branch) during the 2026-06-11 history merge to avoid a number collision with the existing #0185. Commit messages that reference #0185 from that branch refer to this issue._

## Description

About 22 seconds after app launch (2026-06-10 14:07 run), seven in-flight requests were cancelled at the same moment (`URLError -999 cancelled`) and each was logged at **error** level: `app.bsky.actor.getPreferences` (SavedFeedsStore), three `app.bsky.feed.getFeed` calls for `with-friends`, `whats-hot`, and `mentions` (FeedStore), and two feed-generator resolves (SuggestedFeedsStore). This suggests the views kicked off fetches whose owning tasks were torn down (view identity churn or tab/feed switch) — work started and thrown away on every launch — and that expected `Task` cancellation is reported as if it were a failure.

## Steps to reproduce

1. Launch the Mac app and sign in (or restore a session).
2. Wait on the home feed ~20–30 seconds (or switch feeds/tabs shortly after launch).
3. Stream logs: `/usr/bin/log show --last 1h --predicate 'subsystem CONTAINS "co.sstools.Bluesky" AND messageType == 16' --style compact`

## Expected behavior

- Fetches started at launch either complete or are not started redundantly; switching context early does not discard several in-flight requests every launch.
- Cooperative cancellation (`URLError.cancelled` / `CancellationError`) is not logged at error level — it is either ignored or logged at debug/info, so real failures stand out.

## Actual behavior

Seven error-level entries in one second, e.g.:

```
[co.sstools.Bluesky.beta:SavedFeedsStore] savedFeeds load error: ATError.network(… Code=-999 "cancelled" … xrpc/app.bsky.actor.getPreferences …)
[co.sstools.Bluesky.beta:FeedStore] fetch error: ATError.network(… Code=-999 "cancelled" … getFeed?feed=…/with-friends …)
[co.sstools.Bluesky.beta:FeedStore] fetch error: ATError.network(… Code=-999 "cancelled" … getFeed?feed=…/whats-hot …)
[co.sstools.Bluesky.beta:FeedStore] fetch error: ATError.network(… Code=-999 "cancelled" … getFeed?feed=…/mentions …)
[co.sstools.Bluesky.beta:SuggestedFeedsStore] resolve feed …/whats-hot failed: cancelled
[co.sstools.Bluesky.beta:SuggestedFeedsStore] resolve feed …/thevids failed: cancelled
```

## Attachments

None (log lines inline above).

## Notes

Two distinct fixes may be warranted:

1. **Investigate why the fetches are cancelled at all.** Three different feeds plus preferences cancelled simultaneously ~22s after boot smells like view/`.task` identity churn re-creating stores, or eager prefetch of feeds the user never opened. Echoes resolved #0049 (FeedView task fired twice creating duplicate FeedViewModels) — verify that fix still holds for the multi-feed switcher.
2. **Stop logging cancellation as an error.** Stores should detect `URLError.code == .cancelled` (and `CancellationError`) and skip the `logger.error` call (and any user-facing error state). Affected categories observed: `FeedStore`, `SavedFeedsStore`, `SuggestedFeedsStore`; other stores likely share the pattern.

Unrelated entry from the same run, for the record: `FeedStore fetch error: ATError.xrpc(code: "UpstreamFailure", message: "feed unavailable")` — a server-side feed-generator outage, not a client bug; tracked separately as [#0187](0187.md).

**2026-06-10 update (second run, 14:23, PID 15218):** reproduced on the very first second of the run — not 22s in as first observed. Nine cancellations at 14:23:16: `getPreferences` (SavedFeedsStore), three `getFeed` calls (`with-friends`, `whats-hot`, `mentions`), and **five** SuggestedFeedsStore feed-generator resolves (`whats-hot`, `thevids`, `atproto-devs`, `ATProto-Ideas`, one custom feed). The earlier "22 seconds after boot" framing was wrong — the cancellation burst coincides with initial content load, strengthening the view-identity-churn hypothesis.
