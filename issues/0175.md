## Description

The existing `Bluesky-SwiftUIUITests` target is a stub with two empty test methods and no harness. Screenshots (issue #0174) still require a human to navigate to each screen between captures. The per-screen sign-off issues (#0161–#0172) have no automated verification path at all.

This issue builds the foundation that #0176–#0183 depend on:

1. A **launch-environment scripted navigation driver** that routes the app to any screen before assertions or screenshots begin — no human in the loop.
2. A **UITest harness** with a `launch(script:)` entry point and a `screenshot(screen:)` helper that saves captures to `screenshots/` automatically.

This is the Bluesky equivalent of Batty issue #0158.

## Why this matters

Every UI test and screenshot automation task in this project reduces to one unsolved problem: getting the app into a known screen state before the assertion fires. The existing `screenshot.sh` / `screenshots-all.sh` tools punt this to the developer. A scripted driver eliminates the human step and makes screenshot runs and behavioral regression tests both run unattended in CI or from a single `xcodebuild test` invocation.

## Authentication prerequisite

The driver only operates after the app has a live session (`RootView` is showing `MainTabView`). UI tests must supply credentials via `BLUESKY_TEST_HANDLE` and `BLUESKY_TEST_PASSWORD` environment variables, or pre-populate the keychain using a `XCTestCase.setUp` helper that calls the AT Proto `com.atproto.server.createSession` XRPC and writes the returned JWT to the app's keychain group. Without a session the test suite skips rather than fails.

A dedicated test account (`test.bsky.social` or a local dev PDS instance) should be used — never a personal account.

## Part 1 — Navigation driver

### Surface

The app reads `BLUESKY_UI_TEST_SCRIPT` from `ProcessInfo.processInfo.environment` once. The value is a JSON-encoded array of navigation intents. A `UITestNavigator` (`@Observable` class) receives the decoded intents and exposes navigation bindings that `MainTabView` reads via `.environment(navigator)`.

```jsonc
[
  { "intent": "selectTab", "tab": "notifications" }
]
```

```jsonc
[
  { "intent": "selectTab", "tab": "home" },
  { "intent": "waitForFeedLoad", "minPosts": 1 },
  { "intent": "tapFirstPost" }
]
```

### UITestNavigator

New file: `Bluesky-SwiftUI/UITestNavigator.swift`. Gated at *runtime* on env-var presence — zero overhead when `BLUESKY_UI_TEST_SCRIPT` is absent.

```swift
@Observable final class UITestNavigator {
    var selectedTab: AppTab? = nil
    var shouldOpenSettings = false
    var shouldOpenComposer = false
    var shouldOpenModeration = false
    var shouldOpenBookmarks = false
    var shouldTapFirstPost = false
    var scriptError: String? = nil
    // … more as needed per consumer issue
}
```

`MainTabView` reads `@Environment(UITestNavigator?.self)` and mirrors the navigator's state into its own `@State` bindings once they become non-nil. Only injected when the env var is set; production launches never see the type.

### Initial intent vocabulary

| Intent | Effect | Maps to |
|---|---|---|
| `selectTab(tab:)` | Select `home`, `search`, `messages`, `notifications`, `saved`, or `profile` | `MainTabView.selectedTab` |
| `waitForFeedLoad(minPosts:)` | Spin until `FeedStore.posts.count >= minPosts` or timeout (10 s) | Polls the injected `FeedStore` |
| `tapFirstPost` | Sets `threadURI` to `posts[0].uri` — pushes `ThreadView` | `MainTabView.threadURI` |
| `openSettings` | Pushes `SettingsScreen` from the Profile tab | `MainTabView.showSettings` |
| `openComposer` | Opens `ComposerSheet` | `MainTabView.showComposer` |
| `openModeration` | Pushes `ModerationScreen` | `MainTabView.showModeration` |
| `openBookmarks` | Pushes `BookmarksScreen` | `MainTabView.showBookmarks` |
| `openFirstConversation` | Taps first row in `ConversationListScreen` | XCUIElement tap (no state shortcut) |
| `wait(seconds:)` | Unconditional delay (max 10 s) | `Task.sleep` |

Each intent is a one-case extension; new intents added per consumer issue.

### Error surface

If JSON decoding fails or an intent times out, `navigator.scriptError` is set to the error message. `MainTabView` overlays an `Text(scriptError)` accessibility label `"ui-test-driver-error"` so the test harness can read it with `XCUIApplication().staticTexts["ui-test-driver-error"].exists`.

### Logging

Logger category `"UITestNavigator"`, subsystem `Bundle.main.bundleIdentifier`. Every intent logs before and after dispatch with `ui-test:` prefix so failures are inspectable in Console.app.

## Part 2 — Screenshot harness

New file: `Bluesky-SwiftUIUITests/BlueskyUITestHarness.swift`.

```swift
final class BlueskyUITestHarness {
    let app: XCUIApplication

    func launch(script: [UITestIntent] = [], handle: String, password: String)
    func screenshot(screen: String)  // saves to screenshots/<screen>_<timestamp>.png and attaches to the test
    func waitForMainTabView(timeout: TimeInterval = 15)
    func assertNoScriptError()
}
```

`launch(script:)` JSON-encodes the intent array into `app.launchEnvironment["BLUESKY_UI_TEST_SCRIPT"]` and sets `BLUESKY_TEST_HANDLE` / `BLUESKY_TEST_PASSWORD`.

`screenshot(screen:)` calls `XCUIScreen.main.screenshot()`, saves the PNG to `screenshots/` (using the same naming convention as `screenshot.sh`), and attaches it to the running `XCTestCase` via `XCTAttachment`.

## Automated screenshot runner

New test class `ScreenshotTests` in the UI test target. One `@Test` (or `testCapture_<screen>`) per screen, each using `BlueskyUITestHarness`:

```swift
func testCapture_home() {
    harness.launch(script: [.selectTab(.home), .waitForFeedLoad(minPosts: 1)], ...)
    harness.waitForMainTabView()
    harness.screenshot(screen: "home")
}

func testCapture_notifications() {
    harness.launch(script: [.selectTab(.notifications)], ...)
    harness.waitForMainTabView()
    harness.screenshot(screen: "notifications")
}
// … one per screen
```

Running `xcodebuild test -scheme "Bluesky (Beta)" -testPlan Screenshots` produces a full set of screenshots in `screenshots/` with no human interaction.

## Acceptance criteria

- `BLUESKY_UI_TEST_SCRIPT = [{"intent":"selectTab","tab":"notifications"}]` routes the app to the Notifications tab before the first assertion.
- `waitForFeedLoad` blocks until posts arrive or fails the test after 10 s.
- `ScreenshotTests` produces one PNG per screen in `screenshots/` when run via `xcodebuild test`.
- `BLUESKY_UI_TEST_SCRIPT` absent → `UITestNavigator` is never allocated; no overhead in production.
- Error surface (`ui-test-driver-error` label) is readable from the test process when a script fails.

## Notes

- `UITestNavigator` belongs in the **app target** (not `BlueskyKit`) — it imports `AppTab` from `Bluesky-SwiftUI` which is above any library layer.
- The env-var gate (`ProcessInfo.processInfo.environment["BLUESKY_UI_TEST_SCRIPT"] != nil`) replaces `#if DEBUG` — UI tests run against the Beta build, not a Debug build.
- Test credentials must come from environment variables or a CI secret, never be committed. A `XCTestCase` setUp helper that checks for `BLUESKY_TEST_HANDLE` and calls `XCTSkip` when absent keeps the suite green in environments without credentials.
- `XCUIApplication.screenshot()` vs `XCUIScreen.main.screenshot()`: the latter captures the full physical screen including system UI; the former crops to the app window. Use `XCUIScreen.main` for full-fidelity captures, `app.screenshot()` for app-only captures without status bar / notch.
