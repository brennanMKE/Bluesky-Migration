## Description

`app.bsky.actor.putPreferences` is a **full replacement** of the account's `app.bsky` preference namespace — the PDS deletes every existing preference in the namespace and stores exactly what the request body carries. That is why RN never calls it with a partial array: `@atproto/api`'s `BskyAgent` funnels every preference mutation through an internal `updatePreferences(cb)` helper that fetches the full `preferences` array, applies the change, and writes the **whole array** back under a mutex.

Every `putPreferences` call site in BlueskyKit instead builds a `PutPreferencesRequest` whose `preferences` array contains **only the one preference being changed**. Each such write therefore silently deletes every other server-side preference: saved/pinned feeds, labeler subscriptions, content-label settings, post languages, thread sort, birth date, etc.

## Steps to reproduce

1. On a signed-in account with pinned feeds, change any server preference in the app (e.g. Settings → Languages → Primary post language).
2. `GET app.bsky.actor.getPreferences` (or open My Feeds).
3. The `savedFeedsPrefV2` (and every other preference except the one just written) is gone.

## Expected behavior

Preference writes are read-merge-write: fetch the current full preferences array, replace/insert the affected entries, and `putPreferences` the complete array (RN parity).

## Actual behavior

Single-preference bodies clobber the namespace. Live evidence from the 2026-06-10 gate runs on `rnmigration.bsky.social` (#0065 wrote `postLanguages` twice; #0036-era moderation writes did the same):

- My Feeds shows the saved-feeds empty state — `savedFeedsPrefV2` has no items ([screenshot](0066/myfeeds-empty-saved.png))
- Moderation → Advanced shows "No subscribed labelers" — `labelersPref` is gone ([screenshot](0066/moderation-no-labelers.png))

Found during the #0066 Module 15 iOS gate. Until this is fixed, the #0066 Saved Feeds pin/unpin/reorder check cannot be exercised safely against a live account, and the account's wiped `savedFeedsPrefV2` / `labelersPref` need to be restored once writes are safe.

## Root cause

As filed: `app.bsky.actor.putPreferences` is a full replacement of the `app.bsky` preference namespace, and `PutPreferencesRequest` exposed twelve single-preference initializers (`init(savedFeeds:)`, `init(postLanguages:)`, …) that every call site used directly — each write submitted a one-entry `preferences` array and the PDS deleted everything else. There was also no way to round-trip preference `$type`s the app doesn't model: `GetPreferencesResponse` decoded only known types, so even a client-side merge of its typed views would have dropped unknown entries (e.g. `bskyAppStatePref`).

## Fix

RN-parity read-modify-write, centralized (the `@atproto/api` `BskyAgent.updatePreferences(cb)` pattern: fetch full array → mutate → put full array, under a lock):

- **`JSONValue`** (new, `BlueskyCore/JSONValue.swift`) — loss-preserving raw JSON enum; `GetPreferencesResponse` now also decodes the verbatim server array into `rawPreferences: [JSONValue]`, so unmodeled preference entries survive with key set + values intact.
- **`PutPreferencesRequest`** now has exactly one initializer, `init(merging:applying:)`, which filters the current raw array by the mutation's removal predicate and appends the replacement entries. The single-pref initializers are gone so the wipe can't be reintroduced. **`PreferencesMutation`** carries the predicate + new entries, with factories for every modeled pref (`.savedFeeds`, `.adultContentAndLabels`, `.labelers`, `.mutedWords`, `.threadView`, `.feedView` — keyed by `feed` so other feeds' entries survive — `.contentLanguages`, `.postLanguages`, `.birthDate`, `.interests`, `.postInteractionSettings`).
- **`PreferencesWriter`** (new, `BlueskyKit/PreferencesWriter.swift`) — shared actor that serializes get → merge → put process-wide via a task chain (RN's `#prefsLock`), with a closure form that receives the fresh `GetPreferencesResponse` and can return `nil` to skip the write (RN's `cb → false`).
- All 12 call sites converted to `PreferencesWriter.shared.update(...)`; `SessionManager.callPutPreferences` (pre-`NetworkClient` createAccount leg) does its own GET + merge + PUT via `URLSession`.

## Gotchas

- A keyed `Decodable` container can decode the same key twice — `GetPreferencesResponse` decodes `preferences` once into typed helpers and once into `[JSONValue]`. No re-fetch needed.
- An actor alone does **not** serialize an async read-modify-write (actor reentrancy suspends at every `await`); `PreferencesWriter` chains unstructured tasks (`tail`) so each update awaits its predecessor across both network legs.
- `feedViewPref` and `contentLabelPref` are multi-instance `$type`s. `feedView` mutations must remove by (`$type`, `feed`) or they'd wipe other feeds' prefs; content labels are replaced as a full set because `ModerationStore` loads the complete list before mutating.
- `TEST_RUNNER_…` variables must be in `xcodebuild`'s **process environment** (`env TEST_RUNNER_X=… xcodebuild test …`); passing them as `KEY=VALUE` command-line build settings does not reach the test runner.
- The live account's prefs were already wiped pre-fix; the live leg re-seeded `savedFeedsPrefV2` (Discover, pinned). `labelersPref` is still empty — restoring it is gated on #0202.
