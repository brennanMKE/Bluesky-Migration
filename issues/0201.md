# 0201 — `putPreferences` writes single-preference bodies, wiping all other server preferences

| | |
|---|---|
| **Status** | open |
| **Module** | BlueskyCore / BlueskySettings / BlueskyFeed / BlueskyModeration / BlueskyAuth |
| **Platform** | All |
| **First seen** | 2026-06-10 |

## Description

`app.bsky.actor.putPreferences` is a **full replacement** of the account's `app.bsky` preference namespace — the PDS deletes every existing preference in the namespace and stores exactly what the request body carries. That is why RN never calls it with a partial array: `@atproto/api`'s `BskyAgent` funnels every preference mutation through an internal `updatePreferences(cb)` helper that fetches the full `preferences` array, applies the change, and writes the **whole array** back under a mutex.

Every `putPreferences` call site in BlueskyKit instead builds a `PutPreferencesRequest` whose `preferences` array contains **only the one preference being changed**. Each such write therefore silently deletes every other server-side preference: saved/pinned feeds, labeler subscriptions, content-label settings, post languages, thread sort, birth date, etc.

## Steps to reproduce

1. On a signed-in account with pinned feeds, change any server preference in the app (e.g. Settings → Languages → Primary post language).
2. `GET app.bsky.actor.getPreferences` (or open My Feeds).
3. The `savedFeedsPrefV2` (and every other preference except the one just written) is gone.

## Expected behavior

Preference writes are read-merge-write: fetch the current full preferences array, replace/insert the affected entries, and `putPreferences` the complete array (RN parity).

## Actual behavior

Single-preference bodies clobber the namespace. Live evidence from the 2026-06-10 gate runs on `rnmigration.bsky.social` (#0065 wrote `postLanguages` twice; #0036-era moderation writes did the same):

- My Feeds shows the saved-feeds empty state — `savedFeedsPrefV2` has no items ([screenshot](0066/myfeeds-empty-saved.png))
- Moderation → Advanced shows "No subscribed labelers" — `labelersPref` is gone ([screenshot](0066/moderation-no-labelers.png))

## Notes

Call sites that send partial bodies (all via `PutPreferencesRequest` in `BlueskyCore/Moderation.swift:587`):

- `BlueskyCore/Moderation.swift` — `init(adultContentEnabled:contentLabels:)`, `init(savedFeeds:)`, plus the threadView / feedView / postLanguages / contentLanguages / birthDate / labelers initializers
- `BlueskySettings/ThreadPreferencesScreen.swift:209`
- `BlueskySettings/FollowingFeedPreferencesScreen.swift:189`
- `BlueskySettings/LanguageSettingsScreen.swift:249, 272`
- `BlueskySettings/AccountSettingsScreen.swift:399` (birthDate)
- `BlueskyFeed/SavedFeedsStore.swift:73` (pin/unpin/reorder via My Feeds)
- `BlueskyModeration/ModerationStore.swift` (adult content / content labels / labelers)
- `BlueskyModeration/LabelerProfileStore.swift:77, 96`
- `BlueskyOnboarding/OnboardingModel.swift:243`
- `BlueskyAuth/SessionManager.swift:148`

Suggested fix: a single `PreferencesWriter` (read `getPreferences` → mutate the decoded full array → write it back, serialized) that all stores share; `PutPreferencesRequest`'s single-pref initializers should be removed so the wipe can't be reintroduced.

Found during the #0066 Module 15 iOS gate. Until this is fixed, the #0066 Saved Feeds pin/unpin/reorder check cannot be exercised safely against a live account, and the account's wiped `savedFeedsPrefV2` / `labelersPref` need to be restored once writes are safe.
