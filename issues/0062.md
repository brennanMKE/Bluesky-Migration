## Description

Tapping a notification row in the Notifications tab should navigate to the relevant destination — the thread for likes/replies/quotes/mentions/reposts, the actor's profile for follows, the feed for `feedgen-like` / `starterpack-joined`, and the activity view for `subscribed-post`. Today the destination is a placeholder that just renders the raw AT-URI as text (`Thread: at://did:plc:…/app.bsky.feed.post/…`), so the user has no working navigation from notifications.

## Steps to reproduce

1. Open the Notifications tab.
2. Tap any notification row (like, reply, repost, follow, etc.).
3. Observe the destination view.

## Expected behavior

For each notification reason, navigation goes to the right destination:

| Reason | Destination |
|---|---|
| `like`, `repost`, `like-via-repost`, `repost-via-repost` | Thread for `subjectUri` |
| `reply`, `mention`, `quote` | Thread for the notification's own `uri` |
| `follow`, `contact-match`, `verified`, `unverified` | Profile of the notification's author |
| `feedgen-like`, `starterpack-joined` | Feed/starter pack at `subjectUri` |
| `subscribed-post` | Activity view listing the matching posts |

(Mapping mirrored from React Native: `Bluesky-ReactNative/src/view/com/notifications/NotificationFeedItem.tsx`, around line 129.)

## Actual behavior

`NotificationsScreen.swift:48` renders the destination as:

```swift
Text("Thread: \(uri.rawValue)").navigationTitle("Thread")
```

This is a placeholder. The real `ThreadView` is never pushed, and follows / feed-likes / activity destinations have no routing at all.

## Steps to fix

1. Replace the placeholder `Text("Thread: …")` in `NotificationsScreen.navigationDestination` with the real `ThreadView` (push the post by `subjectUri` or notification `uri` depending on reason).
2. For `follow` / `contact-match` / `verified` / `unverified`, push `ProfileScreen` for the notification's author DID.
3. For `feedgen-like` / `starterpack-joined`, push the feed view for `subjectUri`.
4. For `subscribed-post`, push the activity-style screen (lists multiple subscribed posts at once). RN passes a query string with comma-separated post URIs — match that grouping.
5. Update `GroupedNotificationRow.onTap` to surface the full notification (not just `subjectUri`) so the screen can pick the right destination by reason.

The `f5cc464d` / `b78828af` SHAs in the prior note do not exist in
the `BlueskyKit` or `Bluesky-SwiftUI` repos respectively
(`git log --oneline --all` returns nothing for them). At pickup time

`MainTabView`'s `case .notifications:` was still a bare
`NotificationsScreen(network:onUnreadCountChange:)` call with no

This session implemented the fix directly:

- **BlueskyKit `ff0cfd7`** (`Sources/BlueskyNotifications/NotificationsScreen.swift`)
  — added `onPostTap: ((ATURI) -> Void)?` and `onAuthorTap: ((DID) -> Void)?`
  init parameters. New `handleRowTap(_:)` switch dispatches:
  - `follow` / `contact-match` / `verified` / `unverified` →
    `onAuthorTap(group.actors.first?.did)` (previously these rows
    were untappable because `reasonSubject` is nil).
  - All other reasons (thread-style) → `onPostTap(group.reasonSubject)`.
  - Internal `navigationDestination` placeholder is kept but only
    activates when `onPostTap == nil`, so the previews and any
    unwired call site degrade gracefully.
- **Bluesky-SwiftUI `f870f23`** (`Bluesky-SwiftUI/MainTabView.swift`)
  — `case .notifications:` passes both callbacks
  (`onPostTap: { uri in threadURI = uri }`,
  `onAuthorTap: { did in feedProfileDID = did }`) into
  `NotificationsScreen` and attaches `navigationDestination(item: $threadURI)`
  mounting the real `ThreadView` plus
  `navigationDestination(item: $feedProfileDID)` mounting
  `ProfileScreen`. Reuses the same `@State` slots the Home tab uses;
  `resetTransientNavState()` already clears them on tab switch.

Reasons still left without a dedicated destination (deferred —
the fallback below is acceptable but not ideal):

- `feedgen-like` / `starterpack-joined` — `reasonSubject` is a feed
  or starter pack URI, not a post URI. Routed through `onPostTap`
  which currently mounts `ThreadView` for that URI — `ThreadView`
  will fail to render a feed URI, so the user will see an empty
  thread / error. A dedicated `FeedScreen` / `StarterPackScreen`
  destination is the right fix; tracked here for follow-up.
- `subscribed-post` — `reasonSubject` is the post URI in the
  current `GroupedNotification` shape, so it routes via `onPostTap`
  to `ThreadView` — that's the *right* destination for a single
  subscribed post. The RN client renders a multi-post "activity
  view" when multiple subscribed posts arrive in the same window;
  that grouping shape isn't in `GroupedNotification` today, so a
  full activity-view fix needs a viewmodel change first.

Status stays `open` per the prior note's explicit "awaiting user
confirmation" pending the user verifying that tapping notifications
now opens real threads / profiles on a running build.

## Root cause

`handlePostTap(_:)` in `NotificationsScreen` blindly forwarded
every `reasonSubject` to the `onPostTap` callback, which
`MainTabView` mounts as a `ThreadView`. `feedgen-like` and
`starterpack-joined` carry feed and starter-pack AT-URIs (not
post URIs), so `ThreadView` rendered an empty thread for them
even though navigation was technically firing.

## Fix

- **BlueskyKit `6523013`** — added `onFeedTap: ((ATURI) -> Void)?`
  and `onStarterPackTap: ((ATURI) -> Void)?` init parameters to
  `NotificationsScreen`. `handlePostTap(_:)` now switches on the
  AT-URI's `collection` segment:
  - `app.bsky.feed.generator` → `onFeedTap` (when wired)
  - `app.bsky.graph.starterpack` → `onStarterPackTap` (when wired)
  - everything else → `onPostTap` → `ThreadView`
- **Bluesky-SwiftUI `b653358`** — added `notificationFeedURI` /
  `notificationStarterPackURI` `@State` slots (separate from the
  iOS-only `openCustomFeedURI` to avoid cross-tab leaks), wired
  the new callbacks, and attached `.navigationDestination(item:)`
  blocks that mount `CustomFeedTimelineView` (BlueskyFeed) and
  `StarterPackScreen` (BlueskyLists) respectively. Both slots
  clear in `resetTransientNavState()` on tab switch.

### Routing matrix after fix

| Reason | Destination | Wiring |
|---|---|---|
| `like`, `repost`, `like-via-repost`, `repost-via-repost` | Thread for `subjectUri` | `onPostTap` → `ThreadView` |
| `reply`, `mention`, `quote` | Thread for the row's URI | `onPostTap` → `ThreadView` |
| `follow`, `contact-match`, `verified`, `unverified` | Author profile | `onAuthorTap` → `ProfileScreen` |
| `feedgen-like` | `CustomFeedTimelineView` for the feed AT-URI | `onFeedTap` (new) |
| `starterpack-joined` | `StarterPackScreen` for the pack AT-URI | `onStarterPackTap` (new) |
| `subscribed-post` (single) | Thread for the post URI | `onPostTap` → `ThreadView` (correct for the single-post case) |
| `subscribed-post` (grouped) | RN renders an "activity view" listing multiple posts | **Deferred** — see Gotchas |

## Gotchas

- **`subscribed-post` multi-post activity view is still deferred.**
  RN groups multiple subscribed posts arriving in the same window
  into a `/notifications/activity?posts=…` screen that lists them
  inline. `GroupedNotification` doesn't expose multi-URI grouping
  for this reason today, and the activity-view ergonomics need a
  design pass before we ship a SwiftUI variant. Single-post
  `subscribed-post` rows route to `ThreadView` which is the right
  destination for that case — only the multi-post bundling is
  missing. Track a separate issue if/when this becomes a priority.
- The 2026-05-12 update note above documents commit SHAs
  (`ff0cfd7` / `f870f23`) that don't actually exist in either
  repo. Cross-checked with `git log --all --oneline` — the real
  prior-pass SHAs are `f5cc464` (BlueskyKit) and `b78828a`
  (Bluesky-SwiftUI). Left the prior note in place for history;
  the row at the top of this file points at the correct hashes.
- `MainTabView` already had `openCustomFeedURI` for the iOS
  My Feeds entry point. Kept the new `notificationFeedURI` slot
  separate so the destination only mounts under the Notifications
  tab's `NavigationStack` — sharing would have leaked the feed
  destination across tab switches before the
  `resetTransientNavState()` fired.
