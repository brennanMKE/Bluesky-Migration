## Description

Discovered while writing the search UI test suite (#0179). The Search tab in `MainTabView` mounts `SearchScreen(network:)` without supplying the `onActorTap` / `onPostTap` navigation callbacks, so tapping a People result or a post result in search does not push a profile or a thread. The result rows render but are navigational dead ends.

## Steps to reproduce

1. Run the app and open the Search tab.
2. Type a query that returns People and Post results.
3. Tap an account result, then tap a post result.

## Expected behavior

Tapping an account result pushes that user's `ProfileScreen`; tapping a post result pushes the corresponding `ThreadView` — matching the routing already wired for the feed and notifications tabs.

## Actual behavior

Nothing happens on tap; `SearchScreen` has no destination callbacks wired from the app shell.

## Notes

- The #0179 suite covers this with `testTappingAccountResultNavigatesToProfile` / `testTappingPostResultNavigatesToThread`, which currently **skip** cleanly. Wiring the callbacks here will let those tests activate.
- Fix likely mirrors the notifications-tab pattern in `Bluesky-SwiftUI/Bluesky-SwiftUI/MainTabView.swift` (hoisting `onPostTap` / `onAuthorTap` up to the app shell so `BlueskySearch` need not import `BlueskyFeed`/`BlueskyProfile`).
- Reference: `SearchScreen` init in `BlueskyKit/Sources/BlueskySearch/SearchScreen.swift`.

## Root cause

`SearchScreen` already exposed `onActorTap` / `onPostTap` closures (and the
hashtag/topic ones), but the `.search` case in `MainTabView.tabContent`
mounted it as `SearchScreen(network: env.network)` — no callbacks, no
`navigationDestination`s. With both closures `nil`, the People-row `Button`
and the post-card open-thread tap fired into the void, so result rows were
navigational dead ends. Every other content tab (Home, Notifications, Saved)
hoists these destinations to the app shell; the Search tab was simply never
wired.

Secondary finding surfaced while verifying: `PostCard`'s open-thread tap was a
bare `.onTapGesture` on the inner content region. A real finger tap fires it,
but a synthetic XCUITest `.tap()` on the combined accessibility element does
not — so the post-result navigation could not be exercised by the UI test
even after the callbacks were wired.

## Fix

- `Bluesky-SwiftUI/Bluesky-SwiftUI/MainTabView.swift`: wire the `.search` case
  exactly like the Notifications tab — `onActorTap: { feedProfileDID = $0.did }`
  and `onPostTap: { threadURI = $0.uri }`, plus the `navigationDestination`s for
  `feedProfileDID` (→ `ProfileScreen`), `threadURI` (→ `ThreadView`), and the
  liked-by / reposted-by / quotes destinations a pushed thread can reach. No
  new `BlueskySearch` imports of `BlueskyProfile`/`BlueskyFeed`.
- `BlueskyKit/Sources/BlueskyUI/PostCard.swift`: promote the open-thread tap
  region to a button-trait accessibility element with an explicit
  `.accessibilityAction` that invokes the same `onTap`, exposed as
  `post-open-thread` only when an `onTap` is wired. Fixes the synthetic-tap
  gap and improves VoiceOver parity (the post body is now an activatable
  "open thread" target). No behavior change for read-only cards (notification
  rows), which leave `onTap` `nil`.
- `Bluesky-SwiftUIUITests/SearchUITests.swift`: the two navigation tests now
  **assert** the push (fail on regression) instead of skipping when the
  destination doesn't appear; the post test taps the new `post-open-thread`
  button.
