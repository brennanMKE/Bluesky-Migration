## Description

The composer sheet (`ComposerSheet`) has stale-state bugs (#0151 — opens with stale pre-filled text), and the full feature set (video picker, link card preview, thread composer, draft persistence) is in-progress (#0034). A UI test suite asserts the composer opens cleanly with an empty text field, character count is correct, the Post button enables only when text is non-empty, and cancellation closes without posting.

Depends on #0175 (foundation).

## Regressions this suite would have caught

- **#0151** — Composer opened with stale text pre-filled when no draft was resumed. A test asserting `composer-text-field` is empty on fresh open would have caught it immediately.
- **#0034 (in-progress)** — As each composer feature lands (link card, thread mode, draft persistence), the corresponding test case locks it in. Starting the suite now means the baseline is already green when new features are added.

## Test cases

All tests use the #0175 harness. `launch(script: [.selectTab(.home), .openComposer])`.

### Composer opens clean

- **Composer sheet appears.** Assert `composer-sheet` exists within 2 s.
- **Text field is empty on fresh open.** Assert `composer-text-field.value == ""`.
- **Character count starts at 0.** Assert `composer-char-count` label shows `"0 / 300"` (or equivalent format).

### Text input and Post button state

- **Post button disabled when text field empty.** Assert `composer-post-button.isEnabled == false` initially.
- **Post button enables after typing.** Type "Hello" into `composer-text-field`. Assert `composer-post-button.isEnabled == true`.
- **Character count updates.** After typing 5 characters, assert count label shows `"5 / 300"`.
- **Approaching limit shows warning.** Type 280+ characters. Assert `composer-char-count` label is non-green (color is not assertable via XCUITest; assert the count value is ≥ 280 and ≤ 300).

### Cancel closes without posting

- **Cancel dismisses the sheet without navigating.** Tap `composer-cancel-button`. Assert `composer-sheet` no longer exists. Assert feed is still visible and unchanged.

### Screenshot

- `screenshot(screen: "composer-empty")` — before typing.
- `screenshot(screen: "composer-with-text")` — after typing a short post.

## Notes

- Do not actually submit a post during testing against the production `bsky.social` PDS — a `.test` domain or local PDS is required, or tests should be tagged `@network-write` and excluded from default CI runs.
- The `openComposer` intent sets `MainTabView.showComposer = true` via `UITestNavigator`. The composer sheet is presented via `.sheet(isPresented: $showComposer)` in `MainTabView`, so the intent fires correctly from any tab.

## Root cause

Not a bug — this is the planned composer UI test suite (#0182), the seventh of the #0176–#0183 series built on the #0175 harness. The composer (`ComposerSheet`) had no UI-test coverage, so regressions like #0151 (stale pre-filled text on fresh open) and the in-progress #0034 feature work could land silently. The suite locks in the baseline behaviour.

## Fix

Added `Bluesky-SwiftUIUITests/ComposerUITests.swift` (11 tests) on the existing harness, plus five minimal `.accessibilityIdentifier(...)` handles in `BlueskyKit`'s `ComposerSheet.swift`. The existing `openComposer` intent was already fully wired (`UITestNavigator.shouldOpenComposer` → `MainTabView.showComposer`), so no new intent was needed.

Tests:

- **Opens clean** — `testComposerSheetOpens`, `testTextEditorEmptyOnFreshOpen` (#0151 guard), `testCharacterCountStartsAtZero`.
- **Text + Post-button state** — `testPostButtonDisabledWhenEmpty`, `testPostButtonEnablesAfterTypingAndCountUpdates` (count → 5 after "Hello"), `testPostButtonDisabledWhenOverLimit` (305 chars → counter reads 305, Post disabled).
- **Cancel** — `testCancelDismissesEmptyComposer` (empty composer has no draftable content, so Cancel dismisses directly; sheet gone, main tab view still visible).
- **Submission** — `testPostSubmissionEndToEnd`, gated off by default (see below).
- **Screenshots** — `composer-empty`, `composer-with-text`, `composer-empty-dark`.

### Identifiers added (BlueskyKit `ComposerSheet.swift`, commit b2a9739)

- `composer-sheet` — NavigationStack root, for sheet open/dismiss assertions.
- `composer-text-editor` — primary `TextEditor`.
- `composer-char-count` — `CharProgressRing` wrapper. The ring is an `accessibilityElement(children: .ignore)` element whose stock value is "N remaining of 300"; the wrapper now re-states an explicit `"<used>/300"` accessibility value the test parses deterministically.
- `composer-post-button` — submit button (so `isEnabled` is assertable).
- `composer-cancel-button` — cancel affordance.

### Submission approach

Approach (b): the end-to-end submit test is **gated off by default** and skips with a clear message unless `BLUESKY_ENABLE_POST_SUBMIT=1` is set. When enabled it posts exactly one timestamped marker (`UITest <ISO8601>`) — never more than one per run — so the entry is easy to find and delete. The default verification run created **no posts**; the live test account's feed stays clean.

## Gotchas

- **The character counter is not "X / 300".** `CharProgressRing` mirrors RN's `CharProgress`: it shows just the ring fill until ≤ 20 chars remain, then shows the *remaining* count (e.g. "20", "-5"), with the raw count only in its accessibility value as "N remaining of 300". The spec's `"0 / 300"` literal label does not exist on screen. Rather than reshape the production UI, the `composer-char-count` wrapper re-states an explicit `"<used>/300"` accessibility value the test parses — the visible RN-parity ring is unchanged.
- **Cancel with content shows a save prompt, not an immediate dismiss.** When `hasDraftableContent` is true, tapping Cancel presents a "Save Draft / Discard / Keep Editing" confirmation dialog (RN parity, #0151 follow-up). The cancel test therefore exercises the *empty* composer, which dismisses directly. A has-text cancel would need to tap "Discard" in the dialog.
- **No exact `iPhone 17` is the default name across runtimes**, but a plain "iPhone 17" device exists alongside the Pro variants; `name=iPhone 17` resolves correctly.
- **Over-limit typing is slow.** `testPostButtonDisabledWhenOverLimit` types 305 chars via `typeText`, taking ~12s — the longest test in the suite but well within timeouts.
