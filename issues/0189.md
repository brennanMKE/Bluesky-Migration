# 0189 — "Modifying state during view update" — `MainTabView.savedStoreOrCreate()` mutates `@State` inside body evaluation

| | |
|---|---|
| **Status** | open |
| **Module** | Bluesky-SwiftUI |
| **Platform** | All |
| **First seen** | 2026-06-10 |

## Description

Xcode runtime warning "Modifying state during view update, this will cause undefined behavior." at `MainTabView.swift:1042`. `savedStoreOrCreate()` lazily creates the shared `BookmarksStore` and assigns it to the `@State var savedStore` — but it's called from inside the `.navigationDestination(isPresented: $showBookmarks)` view-builder closure (`store: savedStoreOrCreate()` at ~line 1017), so the state write happens during view body evaluation.

## Steps to reproduce

1. Run the Mac app, sign in.
2. Navigate to Saved/Bookmarks (sidebar Saved entry or Profile menu) so the `navigationDestination` content builds.
3. Observe the purple runtime warning in Xcode at `MainTabView.swift:1042`.

## Expected behavior

No state mutation during view update. The shared `BookmarksStore` is created outside body evaluation, and the lazy-shared-instance behavior (one store reused across the sidebar Saved tab and Profile menu entry points, per the comment on `savedStoreOrCreate()`) is preserved.

## Actual behavior

`savedStore = store` executes mid-update; SwiftUI flags undefined behavior. Symptoms of this class of bug include dropped state writes, redundant re-renders, and navigation glitches.

## Notes

There may be a misunderstanding of SwiftUI here which is covered by the updated Swift guidance — consult the `swift-guidance` skill (Observation state-mutation rules / "Modifying state during view update") before fixing; this lazy create-in-body pattern is one of its documented anti-patterns.

Fix directions that keep the single-shared-instance behavior:

- Create the store before presentation: set `savedStore` at the point that flips `showBookmarks = true` (button/menu action — a safe place to write state), and have the destination read the existing store.
- Or hoist ownership out of the view: create `BookmarksStore` alongside the other stores in the app bootstrap / environment so `MainTabView` never owns or lazily instantiates it.
- Audit `MainTabView` (and other `navigationDestination`/sheet builders) for the same pattern — any `xOrCreate()` helper that writes `@State` and is called from a `ViewBuilder` has the same bug.

Observed on the 2026-06-10 Beta run while validating; filed from the Xcode runtime-issue warning, not the unified log.
