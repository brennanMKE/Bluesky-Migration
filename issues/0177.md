## Description

Thread view (`ThreadView`) is the second most navigated screen and has accumulated visual and behavioral regressions — collapsed rows and broken connector lines (#0045), no focal post emphasis (#0146), no reply-sort dropdown (#0140), thread-gate hidden replies not honored (#0145). Several of these only appear at runtime with real post data. A UI test suite locks in thread structure, focal post rendering, and action button behavior.

Depends on #0175 (foundation).

## Regressions this suite would have caught

- **#0045** — Thread view styling broken: collapsed rows, connector lines, dark mode failure. A test asserting reply cells below the focal post exist and have non-zero height would have caught the collapsed-row regression.
- **#0054** — Cannot tap a reply to navigate deeper into a thread. A test tapping the first reply cell and asserting `ThreadView` pushes again would have caught it.
- **#0140** — Thread view has no reply-sort dropdown. A test asserting `thread-sort-menu` exists on the focal post row locks in the presence of the control.
- **#0145** — Thread-gate hidden replies not shown. A test on a known thread with hidden replies asserting the `hidden-reply-notice` accessibility element exists would catch regressions in gate rendering.

## Test cases

All tests use the #0175 harness. `launch(script: [.selectTab(.home), .waitForFeedLoad(minPosts: 1), .tapFirstPost])`.

### Thread structure

- **Thread view shows a focal post.** Assert `thread-focal-post` accessibility identifier exists.
- **Thread view shows at least one reply cell below the focal post.** Assert `thread-reply-cell` count ≥ 1 (conditional on the first post having replies; use a pinned test post URI via `BLUESKY_TEST_POST_URI` env var for determinism).
- **Action bar present on focal post.** Assert `post-action-like`, `post-action-repost`, `post-action-reply`, `post-action-share` exist on the focal post row.
- **Sort menu present.** Assert `thread-sort-menu` exists.

### Navigation from thread

- **Tapping a reply cell pushes deeper thread.** Tap first `thread-reply-cell`. Assert a new `thread-focal-post` element exists (deeper push).
- **Back navigation returns to feed.** Swipe back / tap back. Assert `thread-focal-post` no longer exists at that nesting level.

### Screenshot

- `screenshot(screen: "thread-view")` — captured after `tapFirstPost` settles.
- `screenshot(screen: "thread-view-dark")`.

## Notes

- A pinned, stable test post URI (`BLUESKY_TEST_POST_URI`) makes thread tests deterministic. Without it, the first feed post is whatever the algorithm serves — may have zero replies.
- Focal post emphasis (larger avatar, larger text, full date, expanded stats per #0146) should have accessibility identifiers (`thread-focal-post-stats-row`) so tests can assert presence.
- Reply connector lines are visual-only and not XCUITest-assertable; screenshot capture is the regression check for those.

## Root cause

Not a defect — feature work. The thread view had no UI-test coverage. ThreadView
(`thread-view`), PostCard, and FocalPostCard already carried some identifiers
from #0176, but the focal post, reply cells, and reply-sort menu had no
identifiers a suite could assert on, and FocalPostCard's action bar carried no
`post-action-*` identifiers (unlike the feed PostCard).

## Fix

Added a `ThreadViewUITests` suite plus the minimal accessibility identifiers it
needs.

BlueskyKit (sanctioned identifier-only changes):
- `thread-focal-post` on `FocalPostCard` (with `accessibilityElement(children:
  .contain)`), plus `post-action-reply/repost/like/bookmark/share` identifiers
  and like/repost a11y values on its action bar (mirroring `PostCard`).
- `thread-reply-cell` on each `TreeReplyRow` in `ThreadView`.
- `thread-sort-menu` on the reply-sort toolbar `Menu` in `ThreadView`.

Bluesky-SwiftUI:
- `Bluesky-SwiftUIUITests/ThreadViewUITests.swift` — drives
  `[.home, .waitForFeedLoad(1), .tapFirstPost]` and covers thread structure
  (focal post, action bar, sort menu, reply cells), navigation (tap a reply to
  push a deeper thread), action buttons (focal like tappable/handled, reply
  opens composer), and light/dark screenshots. Reply-dependent tests skip
  cleanly when the algorithm serves a reply-less first post (no pinned post URI
  plumbed). The like assertion stays within 0177's "present and tappable" scope
  (the strict like→unlike value-flip lives in HomeFeedUITests #0176) to avoid
  coupling to a flaky network unlike round-trip.

No new `UITestIntent` cases were needed; the existing `tapFirstPost` intent
already pushes `ThreadView`. The new file is auto-included via the synchronized
UI-test group (no `project.pbxproj` edit).
