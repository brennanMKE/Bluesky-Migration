## Description

macOS mirror/foundation for the UI-test automation built in #0175 (which was implemented and verified on the iOS Simulator only). This issue covers making the `UITestNavigator` driver and `BlueskyUITestHarness` work against the **macOS** app, and getting the suite to actually build-sign-run on the Mac. The macOS app uses a different navigation shell than iOS (sidebar / `NavigationSplitView`, toolbar, multi-window, hover states) rather than the iOS `TabView` + bottom tab bar, so the driver's tab/selection and push intents need a macOS path.

This issue blocks #0187–#0194 (the macOS suite mirrors).

## Scope

- **Signing (prerequisite).** The macOS test build currently fails: `Entitlement com.apple.developer.aps-environment not found and could not be included in profile`. Automatic signing can't produce a provisioning profile because no Apple ID / team is configured in Xcode (`IDEProvisioningTeams` empty). Resolve by either (a) signing the team `XV8BAAVZ6V` Apple ID into Xcode → Settings → Accounts so automatic signing provisions the Push + App-Group entitlements and registers this Mac, or (b) a local-signing test configuration (separate entitlements without Push + App Group) so the macOS app ad-hoc-signs and runs without an account. Decide and document which.
- **Driver on macOS.** Confirm `selectTab`, `tapFirstPost`, `openSettings`, `openModeration`, `openComposer`, `openBookmarks`, `openFirstConversation`, `waitForFeedLoad` drive the macOS navigation shell. Adapt `MainTabView` (or the macOS shell view) to mirror navigator state the same way it does on iOS. Note #0185 (openSettings/openModeration unreliable) likely needs handling here too.
- **Harness on macOS.** Confirm `launch`, `waitForMainTabView`, `screenshot`, `assertNoScriptError` work with the macOS window. Screenshots should capture the macOS window.
- **Run target.** `xcodebuild test -scheme "Bluesky (Beta)" -testPlan Screenshots -destination 'platform=macOS' BLUESKY_TEST_HANDLE=… BLUESKY_TEST_PASSWORD=…` produces a clean run.

## Verification

`xcodebuild test … -destination 'platform=macOS'` runs the foundation tests (`UITestNavigatorTests`, `ScreenshotTests`) green on the Mac.

## Notes

- Mirrors #0175. The app + all 9 iOS suites already **compile** for macOS (verified via `build-for-testing` with signing disabled); only the run path (signing + macOS nav) is open.
- Shared accessibility identifiers added during #0176–#0183 are platform-agnostic and should be reused.

### 2026-05-25 — signing fixed; automation-permission blocker remains

Progress (status stays `open` / in-progress):

- **Signing fixed** (Bluesky-SwiftUI commit `0c9dd12`). Root cause: the project-level `CODE_SIGN_ENTITLEMENTS` in `Build.xcconfig` applied the app's entitlements (incl. `aps-environment` / App Group) to the **UI-test target**, which can't be provisioned with a push-enabled profile — so `build-for-testing` on macOS failed even though the app target builds/runs. Fix clears `CODE_SIGN_ENTITLEMENTS` for the `Bluesky-SwiftUIUITests` Debug+Release configs; the app target keeps its real entitlements.
- **macOS test BUILD now succeeds.** `xcodebuild build-for-testing -scheme "Bluesky (Beta)" -testPlan Screenshots -destination 'platform=macOS' -allowProvisioningUpdates` → `TEST BUILD SUCCEEDED`; the app provisions via *"Mac Team Provisioning Profile: co.sstools.Bluesky.beta"*. Note: CLI runs require **`-allowProvisioningUpdates`** (the Xcode GUI does this implicitly).
- **Remaining blocker — macOS automation permission.** The test RUN fails: *"The test runner failed to initialize for UI testing. (Underlying Error: Timed out while enabling automation mode.)"* This is a macOS TCC Accessibility/Automation permission for the XCUITest runner — a one-time grant (run the UI tests once from Xcode to trigger the approval prompt, or grant Accessibility in System Settings → Privacy & Security), and the run must happen in an active GUI login session. Not a code issue. Once granted, re-run the command above (without `build-for-testing`, as `test`) to verify the foundation suites, then #0187–#0194 can proceed.

### 2026-06-10 — new run blocker: signing cert private key missing; macOS test build still compiles

Re-attempted the macOS `test` run (`-only-testing:…/UITestNavigatorTests`, no credentials). The run no longer reaches the TCC automation-mode step — it now fails **earlier, at the signing/build phase**, on a keychain/certificate problem that did not exist on 2026-05-25:

```
error: Revoke certificate: Your account already has an Apple Development signing
certificate for this machine, but its private key is not installed in your keychain.
Xcode can create a new one after revoking your existing certificate.
(in target 'Bluesky-SwiftUIUITests' / 'Bluesky-SwiftUI')
error: No signing certificate "Mac Development" found: No "Mac Development" signing
certificate matching team ID "XV8BAAVZ6V" with a private key was found.
Testing cancelled because the build failed.  ** TEST FAILED **
```

This is an **environment / keychain** state change, not a code regression: the
"Apple Development" certificate registered to this Mac no longer has its private
key in the login keychain, so automatic signing cannot sign the test runner.
Resolution is GUI/keychain-only and must be done in an interactive login session:
either let Xcode revoke + reissue the certificate (Xcode → Settings → Accounts →
Manage Certificates, or accept the revoke prompt on a GUI `test` run), or import
the existing certificate's private key (`.p12`) back into the login keychain. CLI
`-allowProvisioningUpdates` cannot create a *signing certificate* without the
account's interactive consent.

- **Code is not the blocker.** `xcodebuild build-for-testing … -destination
  'platform=macOS' CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO` →
  `** TEST BUILD SUCCEEDED **`. All targets (app + `Bluesky-SwiftUIUITests`) and
  all 9 suites compile cleanly for macOS.
- **Cross-platform driver gap fixed (code-side prep for #0187).** Added
  `tab(_:)` / `tapTab(_:)` to `BlueskyUITestHarness` so primary-nav taps resolve
  on either shell — iOS tab-bar `Button`s **or** macOS sidebar `cells`. The one
  suite that tapped tabs by literal `app.buttons["Home"]/["Search"]`
  (`HomeFeedUITests.testNoDuplicateCellsAfterTabSwitch`) now uses `tapTab`, so it
  is no longer iOS-only. Re-verified `build-for-testing` on macOS still succeeds.
- **Blocked, not closeable.** Status stays `open`. Two interactive prerequisites
  remain before #0187–#0194 can be *run* on macOS: (1) restore the Mac Development
  signing certificate's private key, then (2) grant the XCUITest runner the TCC
  automation permission (the 2026-05-25 blocker). Both require a GUI login session;

### 2026-06-10 (later) — signing restored + host-resolution bug fixed; only the TCC grant remains

With the signing certificate's private key re-added to the login keychain, the
macOS `test` run got past signing and surfaced a **third, code-level** blocker
(now fixed), then bottomed out on the original TCC permission.

- **Host-resolution bug (FIXED).** After signing succeeded the run failed with:
  *"The bundle identifier for Bluesky.app couldn't be read. No such file or
  directory: …/Debug/Bluesky.app."* Root cause: the app target's `productReference`
  (`PBXFileReference`) had a **stale literal `path = Bluesky.app`**, while the
  active Beta config overrides `PRODUCT_NAME` → `Bluesky Beta` (via
  `Build.xcconfig` → `#include? Active.xcconfig` → `Beta.xcconfig`). The macOS
  UI-test host resolver reads that productReference path to locate the host app's
  Info.plist, so it looked for `Bluesky.app` and missed the real `Bluesky Beta.app`.
  iOS resolves the host by other means, which is why the iOS suites were unaffected.
  Fix: `project.pbxproj` productReference `path = "Bluesky Beta.app"`. The macOS
  run now signs, builds, **launches the runner**, and reaches the test phase.
  *(Caveat: the literal can't track a config switch — if Active is ever pointed at
  Prod, which builds `Bluesky.app`, this would need to flip back. The repo runs the
  Beta scheme for testing, so Beta is the correct value now.)*
- **Remaining blocker — TCC automation permission only.** The run now fails solely
  with: `Bluesky-SwiftUIUITests-Runner … Failed to initialize for UI testing:
  "Timed out while enabling automation mode."` The runner process launches but the
  XCUITest harness cannot enable automation mode without the one-time macOS
  Accessibility/Automation grant. Grant it interactively, then re-run:
  - System Settings → Privacy & Security → **Accessibility** → enable the test
    runner (and/or Xcode / the terminal running `xcodebuild`); **or** run the UI
    tests once from Xcode (Product ▸ Test) to trigger the approval prompt.
  - Must be an active GUI login session.
  - Re-run: `xcodebuild test -workspace Bluesky.xcworkspace -scheme "Bluesky (Beta)"
    -testPlan Screenshots -destination 'platform=macOS' -allowProvisioningUpdates
    -only-testing:Bluesky-SwiftUIUITests/UITestNavigatorTests` (credential-free
    foundation suite first; add `BLUESKY_TEST_HANDLE=… BLUESKY_TEST_PASSWORD=…`
    for the session-dependent suites).

### 2026-06-10 (later still) — signing + TCC cleared; real blocker is a flaky macOS launch crash in AVKit SwiftUI

With the cert restored **and** the TCC automation permission granted, the runner
now initializes and **executes tests** on macOS. The foundation suite ran
(`Executed 5 tests, 4 skipped` for missing credentials), leaving one
credential-free failure: `testMalformedScriptSurfacesError`. Root-causing it
uncovered the actual macOS blocker — **the app itself intermittently crashes on
launch**, so XCUITest sometimes sees an app with a menu bar but **zero windows**
(`app.state == runningForeground`, `windows == 0`, `groups == 0`,
`staticTexts == 0`). A captured screenshot showed the `Bluesky Beta` menu bar
active with no app window on screen.

- **Crash signature (SIGABRT / `abort()`):**
  ```
  swift::fatalError → getSuperclassMetadata → _swift_initClassMetadataImpl
   → _AVKit_SwiftUI __swift_instantiateGenericMetadata
   → swift_getAssociatedTypeWitnessSlow → … (main thread, at launch)
  ```
  i.e. a Swift **generic-metadata instantiation failure in `_AVKit_SwiftUI`**.
  AVKit SwiftUI (`VideoPlayer`) is used in `BlueskyUI/VideoEmbedPlayer.swift` and
  `BlueskyFeed/VideoFeedView.swift`.
- **It's intermittent (a metadata race), not deterministic.** Launching the
  built `Bluesky Beta.app` via `open -n` crashed twice, then launched cleanly on
  the next try with no crash report. XCUITest runs show the same flakiness — some
  runs reach the test body (and would pass with the a11y fix below), others fail
  because `app.launch()` aborts before any window exists (a 60 s no-window run).
  `getSuperclassMetadata` aborts at launch are a known class of Swift-runtime
  race around concurrent generic-metadata instantiation of framework SwiftUI
  types. **This is a real, pre-existing app bug** independent of the test
  infra (none of the test-side changes touch AVKit), and it must be fixed before
  the macOS suites can run reliably. Candidate mitigations to try: explicitly link
  `AVKit.framework` in the app target (so its class metadata is registered
  eagerly), and/or pre-warm the `VideoPlayer`/AVKit metadata on the main thread at
  launch. Needs many repeated launches to validate a flaky-crash fix.

**Code fixes landed this pass (Bluesky-SwiftUI, uncommitted):**
- `project.pbxproj` — app `productReference` path `Bluesky.app` → `"Bluesky Beta.app"` (host-resolution fix above).
- `Bluesky_SwiftUIApp.swift` — `ui-test-driver-error` surface is now a small laid-out visible element (red 9pt banner, error-only) instead of a 0×0/transparent one, so AppKit keeps it in the macOS a11y tree.
- `BlueskyUITestHarness.swift` — `tab(_:)` / `tapTab(_:)` cross-platform nav helpers; `scriptErrorElement` matches the error surface by identifier across *any* element type; `waitForMainTabView` / `assertNoScriptError` use it.
- `HomeFeedUITests.swift` — dup-cells test uses `tapTab`.
- `UITestNavigatorTests.swift` — malformed-script test queries by identifier (any type) and calls `app.activate()` after launch.

**Net:** the test *infrastructure* now works on macOS (signs, builds, runs, queries both shells); the gating blocker for #0187–#0194 is the flaky AVKit-SwiftUI launch crash, now tracked separately as **#0195** (a real app-level bug independent of the test infra).

#### Mitigation attempt #1 — did NOT work; reverted

Measured the crash rate by repeatedly launching the built `Bluesky Beta.app`
(`open -n`, 3 s, kill) and counting new crash reports:
- **Baseline:** 5 crashes / 20 launches (~25%).
- **With fix** (`import AVKit` in the app target + `_ = VideoPlayer<EmptyView>.self`
  metadata pre-warm in `App.init()`): **10 / 20 (~50%)** — no improvement (and the
  rapid relaunch test is itself noisy/race-amplifying). Reverted both app-code
  changes; `Bluesky_SwiftUIApp.swift` is back to its original imports/`init`.

Open questions for the next attempt (do NOT validate via rapid `open -n` relaunch —
it amplifies the race and spams the desktop with app windows): the failing
superclass is inside `_AVKit_SwiftUI`, so the pre-warm of `VideoPlayer<EmptyView>`
may target the wrong generic; worth identifying the exact failing type from a
