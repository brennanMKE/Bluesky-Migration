## Description

Opening the Messages tab fails: both the conversation list fetch and the message-requests inbox fetch error with `ATError.xrpc(code: "MethodNotImplemented", message: "Method Not Implemented")`. This is the response a PDS gives for `chat.bsky.*` calls when the `atproto-proxy: did:web:api.bsky.chat#bsky_chat` header is missing, yet `ATProtoClient.applyProxyHeader` exists and appears to cover this case — so either the header isn't reaching the wire, or something else is wrong. Possibly a regression: Module 11 DM live validation (#0033) previously passed.

## Resolution notes

> 🟢 Resolved 2026-06-11 — the app was sending chat requests to the `bsky.social` entryway, which no longer forwards `atproto-proxy` requests; authenticated XRPC now routes to the account's actual PDS host taken from the session response's `didDoc`, matching RN.

## Root cause

Not the proxy header — `applyProxyHeader` was setting `atproto-proxy: did:web:api.bsky.chat#bsky_chat` correctly, and a `curl` repro proved it: `chat.bsky.convo.listConvos` via `https://bsky.social` returned `501 MethodNotImplemented` both **with and without** the header, while the same request against the account's real PDS host (`https://jellybaby.us-east.host.bsky.network`, from the JWT `aud` / session `didDoc`) returned `200` with the header. The app persisted the entryway URL it signed in with (`https://bsky.social`) as `Account.serviceEndpoint` and sent all authenticated XRPC there; the entryway stopped forwarding proxied chat requests sometime after the #0033 validation (2026-05-05), turning this into a regression with no client code change. RN is unaffected because `@atproto/api` extracts the PDS endpoint from the session response's `didDoc` (`getPdsEndpoint`) and routes the agent to `sessionManager.pdsUrl` (persisted per account as `pdsUrl`, see `src/state/session/agent.ts`).

## Fix

Added a minimal `DIDDocument` type to `BlueskyCore` (lossy decoding so malformed `service` entries can't fail a whole session response) with a `pdsEndpoint` accessor that finds the `#atproto_pds` / `AtprotoPersonalDataServer` service entry, RN-style. Surfaced `didDoc` on the `createSession`, `refreshSession`, `getSession`, and `createAccount` responses, and `SessionManager` now prefers `didDoc.pdsEndpoint` over the entryway URL when persisting accounts (login, createAccount, the refresh branch of resumeSession, the getSession merge, and refreshCurrentSession). Accounts persisted before the fix self-heal on next launch: `resumeSession`'s best-effort `getSession` merge adopts the PDS host from the returned `didDoc` and re-saves the keychain record.

## Gotchas

- The server error was misleading: `MethodNotImplemented` is the PDS "missing proxy header" response, but here the header was present and ignored — the entryway (`bsky.social`) simply doesn't proxy. Always compare against the host in the access JWT's `aud` claim before trusting the header theory.
- `ATProtoClient.performRefresh` (the 401-retry path) still saves the account unchanged; it doesn't see `didDoc`. That's fine because `SessionManager` heals the endpoint at every launch, but if the client ever becomes the sole refresher the `didDoc` adoption would need to move there too.
- DID-document `serviceEndpoint` values can legally be objects/arrays per the DID spec; `DIDDocument.Service` decodes field-by-field with `try?` so an exotic entry can't fail the whole `createSession` decode (which would have broken login outright).

## Notes

Code state at filing: `BlueskyNetworking/ATProtoClient.swift` — `applyProxyHeader(_:lexicon:)` (~line 199) sets `atproto-proxy: did:web:api.bsky.chat#bsky_chat` for any lexicon with prefix `chat.bsky.`, and `buildGetRequest` / `buildPostRequest` / `buildUploadRequest` all call it. `ConversationStore.swift` fetches via `network.get(lexicon: "chat.bsky.convo.listConvos", …)`. So the obvious cause (header never added) is not visibly true in source.

Investigation leads, in order:

1. Reproduce with `curl` against `https://bsky.social/xrpc/chat.bsky.convo.listConvos` using the stored access JWT — once with and once without the `atproto-proxy` header — to confirm which side is failing.
2. Check whether the signed-in account uses an **app password without DM access**, and what error that actually yields vs. `MethodNotImplemented`.
3. Check the 401-auto-refresh retry path in `ATProtoClient` — does the retried request preserve the proxy header, or is it rebuilt/copied in a way that drops it?
4. Verify the header survives any request mutation between build and send (e.g. interception, redirects).
5. Compare against RN: `src/lib/constants.ts` (`DM_SERVICE_HEADERS`) and the chat query setup in `src/state/queries/messages/`.
