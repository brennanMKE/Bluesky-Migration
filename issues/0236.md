# 0236 — Feed fetch repeatedly fails with `UpstreamFailure: feed unavailable`; verify retry behavior and error UI

> _Re-homed from **#0187** (Mac/MacBook branch) during the 2026-06-11 history merge to avoid a number collision with the existing #0187. Commit messages that reference #0187 from that branch refer to this issue._

## Description

`FeedStore` logged `ATError.xrpc(code: "UpstreamFailure", message: "feed unavailable")` three times within 24 seconds in a single run (14:23:16, 14:23:25, 14:23:40) — a feed generator that is down server-side is being fetched repeatedly. The failure itself is upstream (not a client bug), but the repetition suggests automatic refetching of a known-bad feed, and it's unverified what the user sees when a pinned feed is unavailable.

## Steps to reproduce

1. Launch the Mac app and sign in (one of the pinned/saved feeds' generators must be down — observed with the saved-feeds set on 2026-06-10).
2. Stay on the Home tab ~30 seconds.
3. Stream logs: `/usr/bin/log show --last 5m --predicate 'subsystem == "co.sstools.Bluesky.beta" AND messageType == 16' --style compact`

## Expected behavior

- An unavailable feed shows a clear inline error state with a manual Retry, matching the RN client's feed error UI; the app does not silently refetch a failing feed on a tight cadence.
- Other feeds and the rest of the app are unaffected.

## Actual behavior

Three `fetch error: BlueskyCore.ATError.xrpc(code: "UpstreamFailure", message: "feed unavailable")` entries from `FeedStore` within 24 seconds. Whether the UI surfaced anything to the user is unverified — the log alone doesn't show which feed failed or what was rendered.

## Attachments

None (log lines inline above).

## Notes

Two things to determine, then fix what's actually wrong:

1. **Which code path fetches the failing feed three times** — feed switcher prefetch of all pinned feeds, `.task` re-firing on view identity churn (see #0185, same launch window), or an automatic retry. The `FeedStore` error log should include the feed URI to make this diagnosable; today it logs the error only.
2. **What the user sees** — confirm `FeedView`'s error state appears for an unavailable feed (RN shows an error card with retry), rather than a spinner or empty list.

Related: #0185 (launch-time fetch churn from the same run); RN reference: feed error handling in `src/view/com/posts/` / `src/state/queries/post-feed.ts`.
