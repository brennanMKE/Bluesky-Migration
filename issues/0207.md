# 0207 — Composer crashes after a successful thread post (stale index in `threadPostSection` binding)

| | |
|---|---|
| **Status** | open |
| **Module** | BlueskyComposer |
| **Platform** | All |
| **First seen** | 2026-06-11 |

## Description

Submitting a thread (root + at least one additional post) crashes the app
immediately after the submit succeeds. The posts land on the PDS correctly —
the crash happens client-side while the composer tears down.

`ComposerSheet.threadPostSection(index:)` builds the extra thread editors with
an unguarded index subscript captured inside a `Binding`:

```swift
// BlueskyKit/Sources/BlueskyComposer/ComposerSheet.swift:958-961
TextEditor(text: Binding(
    get: { viewModel.additionalPosts[index] },
    set: { viewModel.additionalPosts[index] = $0 }
))
```

(`CharProgressRing` at line 968 subscripts the same way.) The thread rows come
from `ForEach(viewModel.additionalPosts.indices, id: \.self)`, so the binding
captures a raw `Int`. On a successful submit `ComposerViewModel` resets
`additionalPosts = []` (ComposerViewModel.swift, post-submit reset); SwiftUI
then re-evaluates the still-mounted `TextEditor`'s binding with the stale
index and `Array._checkSubscript` traps:

```
exception: EXC_BREAKPOINT (SIGTRAP)
libswiftCore  Array._checkSubscript(_:wasNativeTypeChecked:)
libswiftCore  Array.subscript.getter
Bluesky Beta  closure #1 in ... in ComposerSheet.threadPostSection(index:)
SwiftUICore   Binding.ScopedLocation.update() …
```

Full crash report: [crash-after-thread-submit.ips](0207/crash-after-thread-submit.ips).
Composer state just before the submit: [thread-composer-before-submit.png](0207/thread-composer-before-submit.png).

Found during the #0064 gate re-run
(`ComposerGateUITests/test04ThreadPostWithLinkCard`, iPhone 17 simulator,
iOS 26.5, 2026-06-11). The same reset-while-mounted pattern would also fire
on any other path that clears or shrinks `additionalPosts` while the sheet is
on screen (e.g. removing a middle post repositions later indices —
`removePost(at:)` is guarded in the view model but the *bindings* are not).

## Steps to reproduce

1. Sign in, open the composer.
2. Type root text, tap **Add to thread**, type text in the second editor.
3. Tap **Post** and wait for the submit to succeed.

## Expected behavior

Both posts are created (root + reply) and the composer dismisses cleanly,
returning to the feed.

## Actual behavior

Both posts are created on the server, then the app crashes
(`Fatal error: Index out of range`) during composer dismissal.

## Notes

- Server evidence that the submit itself works (from the #0064 re-run):
  root `…/app.bsky.feed.post/3mnyz5qcqlr26` carried the
  `app.bsky.embed.external` card and the reply `…/3mnyz5qzfzr2v` had correct
  `reply.root`/`reply.parent` refs before cleanup deleted them.
- Fix direction: make the row bindings index-safe (e.g.
  `get: { index < viewModel.additionalPosts.count ? viewModel.additionalPosts[index] : "" }`,
  guarded `set:`), or iterate identifiable elements instead of raw indices.
- Blocks the thread leg of the #0064 Module 12 iOS composer gate.
