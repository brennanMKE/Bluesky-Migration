## Description

Creating a list from the Lists hub succeeds server-side, but the hub keeps showing the "No Lists" empty state. `ListsStore.createList` issues `com.atproto.repo.createRecord` and then immediately re-fetches `app.bsky.graph.getLists` — an **AppView** query that has not indexed the just-committed record yet. The empty response overwrites the store, no error is surfaced, there is no optimistic insert and no retry, so the user's new list is invisible until the screen is left and re-entered (or the app relaunched) after indexing catches up.

Reproduced twice during the #0066 gate run (22:16 and 22:28 on 2026-06-10): the record was confirmed on the PDS (`com.atproto.repo.listRecords`) and on the public AppView within seconds, while the hub still rendered "No Lists" 15+ seconds after the Create tap. After a relaunch ~2 minutes later the same hub showed the list ([screenshot](0066/lists-hub-after-relaunch.png)).

## Steps to reproduce

1. Profile → overflow menu → My Lists.
2. Tap +, name a list, tap Create.
3. The hub still shows "No Lists" / "Lists you create will appear here." indefinitely.

## Expected behavior

The new list appears immediately. RN's `useCreateListMutation` returns the created record's `uri`/`cid` and navigates straight to the new list's screen while invalidating the lists query — it never depends on an instant AppView round-trip.

## Actual behavior

Hub stays on the empty state; the list only appears after re-entering the screen once the AppView has indexed the record.

## Notes

- `BlueskyKit/Sources/BlueskyLists/ListsStore.swift` — `createList` ends with `await loadLists(actorDID:)`.
- Fix options: optimistically append a local `ListView` built from the `createRecord` response (RN-parity: navigate into the new list directly), or poll/delay the re-fetch.
- Found during #0066; the same race presumably affects every create-then-refetch flow that reads back through the AppView.

## Root cause

`ListsStore.createList` posted `com.atproto.repo.createRecord` and then immediately re-fetched `app.bsky.graph.getLists`. The PDS commit is synchronous but the **AppView** indexes it asynchronously, so the instant re-fetch routinely returned the stale pre-create set, and `loadLists` overwrote `lists` wholesale with it — no optimistic insert, no retry, no error. The same class of race existed on delete: `deleteList` removed the row locally, but any re-fetch before the AppView caught up would resurrect it.

Upstream RN (`src/state/queries/list.ts`, baseline `46b8a58`) never trusts the instant round-trip: `useListCreateMutation` / `useListDeleteMutation` call `whenAppViewReady` — polling `getList` up to 5×1s until the AppView reflects the write — *before* invalidating the lists query in `onSuccess`.

## Fix

Optimistic local state in `ListsStore` reconciled against fetches (BlueskyKit `b55a930`):

- **Create:** after a successful `createRecord`, build a `ListView` locally from the response `uri`/`cid`, the submitted record fields, and a creator `ProfileView` derived from the stored session account (no network), and insert it at index 0 — `getLists` returns newest-first. The post-create re-fetch is kept: if indexing already caught up the server copy wins.
- **Reconciliation:** `loadLists` now merges each first-page response with session state — optimistic inserts the server hasn't indexed yet are kept at the top and de-duped by URI once the indexed copy arrives; `loadMore` de-dupes pages against rows already shown.
- **Delete:** after a successful `deleteRecord`, the URI is tombstoned and filtered out of every subsequent `getLists` response so a stale page can't resurrect the row (the existing restore-on-failure path is unchanged).

New `ListsStoreTests` suite (4 tests) covers: optimistic insert survives stale re-fetches, reconciliation prefers the indexed server copy without duplicating, delete is not resurrected by a stale page, and create-then-delete before indexing leaves the hub empty. A live regression UI test, `RemainingScreensGateUITests.testListCreateAppearsImmediatelyThenDelete0203` (Bluesky-SwiftUI `c36c87c`), asserts the row within 5 s of the Create tap, then deletes it and confirms no resurrection — fully reversed.

## Gotchas

- `ListView` uses synthesized `Codable`, so `labels` is a **required** key in fixtures/responses (`ProfileView` has a custom decoder that defaults it; `ListView` does not).
- `TEST_RUNNER_…` env vars passed as trailing `xcodebuild` arguments never reach the runner (they become build settings) — pass `BLUESKY_TEST_HANDLE=… BLUESKY_TEST_PASSWORD=…` as build settings instead; the scheme expands them (#0175 notes), and placeholder values suffice when the sim already has a keychain session.
- The optimistic creator profile comes from the stored session account; a keychain read failure deliberately does not abort the insert (the record already exists on the PDS) — it falls back to a DID-only profile and logs.
