## Description

The Notifications screen has had correctness bugs at the data layer (#0063 — reason labels incomplete) and navigation regressions (#0030 — push notification routes to wrong thread). Grouping was added as a feature (#0029); it was never regression-tested. A UI test suite asserts the list loads, reason labels are human-readable, grouping works, and tapping a notification routes to the correct destination.

Depends on #0175 (foundation).

## Regressions this suite would have caught

- **#0063** — `subscribed-post` and other reason codes rendered as raw verbatim strings. A test iterating over visible notification cells and asserting no cell text matches a raw `app.bsky.*` identifier or underscore-prefixed string would have caught it.
- **#0029** — Grouped notifications not implemented. A test asserting `notifications-group-header` cells exist for accounts with multiple interactions of the same type locks in the grouping behavior.
- **#0030** — Push notification taps open the wrong thread. A test simulating a tap-from-notification deep link and asserting the correct post URI is in the navigation stack would catch routing regressions.

## Test cases

All tests use the #0175 harness. `launch(script: [.selectTab(.notifications)])`.

### Notification list

- **Notifications screen loads.** Assert `notifications-screen` exists within 5 s.
- **At least one notification cell visible.** Assert `notification-cell` count ≥ 1 (conditional on the test account having notifications — skip if none).
- **No raw reason codes visible.** Assert no visible static text matches `"app.bsky.\w+"` or `"\w+[_-]\w+"` patterns. (This is the #0063 regression guard.)
- **Grouped notification header cells present.** Assert `notifications-group-header` exists at least once when the test account has ≥ 2 interactions of the same type from different users.

### Tap routing

- **Tapping a like/repost notification navigates to the subject thread.** Tap a `notification-cell` whose reason is `like` or `repost`. Assert `thread-focal-post` appears.
- **Tapping a follow notification navigates to the follower's profile.** Tap a `notification-cell` whose reason is `follow`. Assert `profile-screen` appears.
- **Back navigation from thread returns to Notifications.** Assert `notifications-screen` still in hierarchy after back navigation.

### Screenshot

- `screenshot(screen: "notifications")` — full list.
- `screenshot(screen: "notifications-dark")`.

## Notes

- Tap-routing tests require the test account to have real notifications of specific types. Use `BLUESKY_TEST_SKIP_NOTIFICATION_TAP=1` to skip routing tests in CI environments where the test account is fresh or has no notifications.
- The `reason` field is available as the notification cell's `accessibilityHint` or a sub-label once accessibility identifiers are added to `NotificationRow`.

## Root cause

Not a bug — this is the notifications UI test suite (#0180), the fifth in the
#0175 series (after #0176–#0179). `NotificationsScreen` carried no accessibility
identifiers, so the list, filter strip, grouped rows, and per-reason rows could
not be asserted on or tapped from a UI test.

## Fix

- **BlueskyKit** (`NotificationsScreen.swift`): added UI-test anchors —
  `notifications-screen` (outer container), `notifications-filter-strip`
  (All/Mentions strip), `notification-cell` on every grouped row, a zero-size
  `notification-reason-<reason>` child marker per row (so routing tests can pick
  a like/repost row vs. a follow row), and a `notifications-group-header` marker
  on multi-actor groups (#0029 guard). Rows use
  `.accessibilityElement(children: .contain)` so their child static texts stay
  individually queryable for the #0063 raw-reason-leak guard (an identifier +
  value would fold the subtree into one element and hide that text).
- **Bluesky-SwiftUI** (`NotificationsUITests.swift`): new suite mirroring the
  sibling suites' skip-when-no-creds and skip-when-data-absent patterns. The
  notifications tab's `onPostTap` / `onAuthorTap` were already wired in
  `MainTabView` (pushes `ThreadView` / `ProfileScreen`), so no new navigator
  intent was needed — `launch(script: [.notifications])` is sufficient.
