# 0208 — 401 refresh stampede clobbers the rotated refresh token

| | |
|---|---|
| **Status** | open |
| **Module** | BlueskyNetworking |
| **Platform** | All |
| **First seen** | 2026-06-11 |

## Description

When several in-flight requests hit 401 at once (e.g. feed+notifications+profile polls right after the access JWT expires), each independently refreshes. AT Proto rotates the refresh token, so only the first succeeds; the rest fail and overwrite the freshly-rotated tokens, causing spurious session expiry / forced logout despite a valid session.

## Evidence

`ATProtoClient` (BlueskyNetworking/ATProtoClient.swift) has no in-flight refresh coordination — stored state is only `accountStore`/`session`/`pathMonitor`/`encoder`/`decoder` (no `refreshTask`). Each `perform*` does its own `refreshTokens(stored:)` on 401 (~lines 84/103/123) and `refreshTokens` unconditionally `accountStore.save(updated)` (line 272). N concurrent 401s enter refresh with the same `stored.refreshJwt` before any save lands — a classic stampede with no single-flight guard.

## Suggested fix

Add single-flight: `private var refreshInFlight: Task<StoredAccount,Error>?` on the actor; await an existing task or create one. Re-load the stored account before deciding to refresh (another request may have rotated), and only `save` on success.
